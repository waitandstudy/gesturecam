# 省 token 工作纪律

背景与实测数据见 `docs/DECISIONS.md` §22。核心事实：

> Agent 每一轮都要把**完整对话历史**重发一次，而历史随轮数线性增长
> ⇒ 总消耗是**平方级**的。所以"省 token"唯一有效的方向是
> **减少无依赖的往返次数**，而不是把每次回答写短。

## 一、验证分级（最省钱的一条）

| 改动范围 | 该跑什么 |
| --- | --- |
| 改一个函数/阈值 | `node_modules\.bin\tsc.cmd --noEmit` + **只有相关的那一个**测试文件 |
| 改了公共模块（`handShape` / `gestureManager` / `scene`） | `node_modules\.bin\vitest.cmd run`（全量，约 10 秒） |
| 改动手势/交互/渲染的**行为** | 加跑 `node tools/verify-browser.mjs`（约 4 分钟，76 项）——**一个任务只跑一次，放最后** |
| 只改文档/注释 | 什么都不用跑 |

**不要**在每一小步之后都跑浏览器验收。它 90% 的检查与本次改动无关，
而每跑一次都要按当时已经很臃肿的上下文重新付费。跑之前先问：
"这一轮改动真的可能影响这 76 项里的哪几项？"

> 这条现在是**硬约束**：`PreToolUse` 守卫（`tools/hooks/guard-expensive.mjs`）
> 会在同一会话里第二次调用 `verify-browser.mjs` 时直接阻塞，并把理由交给你。

## 二、禁止"猜着调试"

遇到报错或行为不符时：

1. **先把原始输出/错误原文打出来看**（一次调用）
2. 基于原文提出**一个**假设
3. 验证它

**如果这个假设错了，停下来汇报**，把原始输出交给用户，不要接着试第二个、第三个猜想。
"猜 → 写脚本验证 → 猜错 → 再猜"是本项目历史上最贵的循环
（有一次我为搞清一个文件格式，写了 14 个一次性脚本、猜错三次，最后无功而返，
而答案其实一直就在上下文里）。

推论：**不要为了测量而测量。** 如果某个数字不是"决策所必需"，就不要去挖它。

## 三、读文件

- 先 `grep` 定位行号，再 `read` 带 `offset`/`limit` 只读那一段
- 超过 ~300 行的文件**绝不**整读
- 已经读过并在上下文里的内容不要重复读
- 同名文件在多个位置时，用一次 `glob` 找全，不要逐个试
- **不确定路径/格式时，先读配置或源码确认，不要"试一个位置看看"**
  （把 skill 放错目录、把 `.jsonl.zstd` 当成单帧文件，都是这么浪费掉的）

## 四、合并往返

- 无依赖的调用**放在同一批**（读+读、改+改、搜+搜）
- 不要"读一个 → 改一个 → 再读一个 → 再改一个"这样串行做无依赖的事
- 一次性诊断脚本**用完立刻删**，不要留在 `tools/` 里当资产

## 五、汇报与提问

- 汇报格式：**结论 + 证据 + 下一步**。不重复 `docs/` 里已有的内容
- 需要用户提供信息时，**一次把要的东西列全**（不要一句一轮地问）
- 回答会进入下一轮历史并被反复计费，所以短是硬要求

## 六、长任务该切段，而且要先切

判断标准：**当一件"可交付的独立事情"做完，就该换新会话。**
不要在一个会话里从"指弹标定"做到"Phase 7"。

需要的历史写进 `docs/` —— 新会话读 `AGENTS.md` + 相关 docs 即可无缝接上。

## 七、本项目特有陷阱（重复踩过）

- **只能用 `edit`/`write` 工具改文件**，不要在 PowerShell 里拼字符串改文件
  （中文 + 引号 + 反引号会毁文件，`README.md` 被毁过一次）
- `verify-browser.mjs` 的探针里**不要用嵌套模板字符串**（反引号套反引号），用字符串拼接
- 合成输入必须**按真实时间喂帧**（rAF ≈16ms），不要把"帧数"当时间
- 改了手势阈值后，验收脚本里的硬编码期望值要同步更新
