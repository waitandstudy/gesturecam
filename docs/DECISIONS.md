## 2. 坐标系统（本项目最容易出错的地方，单独写清楚）

全项目只有三套坐标：

| 坐标 | 定义 | 范围 |
| --- | --- | --- |
| **源图像素 source px** | 摄像头原始帧像素，(0,0) 左上 | [0, srcW] × [0, srcH] |
| **场景 scene** | **用户在屏幕上实际看到的那块画面**的归一化坐标，左上原点，y 向下 | [0,1]²，允许越界 |
| **画布像素 canvas px** | 最终渲染目标像素 | [0, cw] × [0, ch] |

### 三条铁律

1. **场景 = cover 裁切后的可见画面。**
   被 cover 裁掉的部分坐标落在 [0,1] 之外 —— 参考文档要的"画面外缓冲区域"
   天然就是越界坐标，不需要额外造一套坐标系。

2. **镜像只作用于两个地方，绝不能进素材矩阵：**
   - `Viewport.createCameraMirrorMatrix()` —— 画摄像头帧时翻转画面本身
   - `Viewport.sourceNormalizedToScene()` —— 把未镜像的关键点换算成"用户看到的位置"

3. **素材内容永不翻转。**
   场景坐标已经定义在"显示后"的空间里，所以场景 → 画布只是一次等比缩放。
   素材矩阵的**行列式必须为正**，有回归测试盯着这件事。

第四条（几何相关）：素材的旋转必须在**等比例的画布像素空间**里做。
scene 的 [0,1]×[0,1] 在非正方形画面上是各向异性的，直接在里面旋转会把图片切成平行四边形。

### 真实 bug 记录：素材被镜像成"反字"

Phase 1 的浏览器验收截图暴露了一个产品级错误：最初我把镜像实现在"统一视图矩阵"里，
摄像头帧和素材一起翻转，结果是**一张写着字的图渲染出来是反的**。
对口播素材（图表、截图、带文字的图）这是灾难。

修正方式就是上面第 2、3 条铁律：镜像属于"显示摄像头"这一步，不属于素材。
同时补了两层防护：
- 单测 `开镜像不会翻转素材内容（回归：反字 bug）` —— 断言素材矩阵行列式为正；
- 浏览器验收里的**像素级探针** —— 测试图左上角画一块白，断言它渲染后仍在左上角。

## 3. 管线与模块映射

两份文档的模块清单合并成一条管线，右侧是当前状态：

```

   ↓

   ↓
GestureManager           📄 Phase 1 契约 + 迟滞原语 · Phase 2 实现
   ↓
```

## 4. 关键设计：行为看不到原始手部关键点

参考文档第四节要求「手势 → 交互事件 → 行为 → 对象」的解耦，第九节要求
「不要让 GestureManager 直接操作 ImageObject 的位置、缩放等属性」。

我把这条规则**做成类型系统的约束**，而不是靠自觉：

- `BehaviorContext` 里**没有** `landmarks`，只有
  `gestures`（已平滑+迟滞的连续量与本帧离散事件）和 `interaction`（本帧交互状态）。
- `InteractionManager` 只产出 `targetPosition`，**从不修改素材位置**。
- 命中测试、抓取偏移、超时释放全在交互层；"怎么动"全在 Behavior。

带来三个好处：
1. 换手感（硬跟手 / 弹簧跟手 / 带惯性摩擦）只需换 Behavior，抓取逻辑完全复用；
2. 行为可以在 Node 里用合成手势状态单测，不需要造假的 21 点关键点数组；
3. 换识别方案（MediaPipe → 别的）时，行为层一行都不用改。

## 5. 与两份需求文档的偏离（都给了理由）

| # | 偏离 | 理由 |
| --- | --- | --- |
| 1 | Camera / HandTracker **不放在 Scene 内部**，由 app 层持有，Scene 每帧以参数接收 `GestureState` | 相机和追踪都绑死 DOM。放进 Scene 会让 Scene 无法在 Node 里单测、无法离线重放。只是"谁持引用"的差异，不影响模块划分与可替换性 |
| 2 | 新增 `ObjectState.interaction = { grabbable, scalable, rotatable }` | 参考文档第五节 Object → Interaction 一节的落地。做成数据后，InteractionManager 里不需要任何"这张图特殊"的分支。且 `ObjectStatePatch` 允许局部覆盖，编排时写 `{ grabbable: false }` 即可 |
| 3 | 新增 `InteractionManager`（第一份文档的模块清单里没有） | 采纳第二份文档第四节的管线 |
| 4 | `BoundaryMode` 保留 `CLAMP`（第一份文档有，第二份没有） | 取并集，第五种策略不增加实现成本 |
| 5 | `FOLLOW_HAND` / `TOP_HANGING` 只留字段不实现 | 第一份文档第十七节把跟随排在 Phase 4、悬挂排在 Phase 7。现在挂载这两种模式的素材会保持静止，并打一条 `console.info` 说明——不假装生效，也不抛错 |
| 6 | 多素材新加入时按固定步长错开排布 | 真正的编排 UI 属于 Phase 14，这里只是让"加三张图"立刻可看 |

## 7. 我对参考指南的两点不同意见（需要你确认）

1. **"双手缩放"的排序。**
   第一份文档的阶段 5 是「食指 + 拇指双指距离变化 → 缩放」，
   第二份文档的阶段 5 是「双手之间距离变化 → 缩放」。
   这是**两个不同的交互**，不是同一件事的两种说法。
   我的建议：**先做单手 pinch 缩放**（抓取本身已经是 pinch，同手势自然延伸，
   用户不用学新动作），双手缩放排到 pinch 手感稳定之后。
   你的两份文档在这里需要统一，我按上述顺序推进，除非你另有决定。

2. **"虚拟摄像头"在 Web 栈上是天花板。**
   `handy` 的核心卖点之一是输出到虚拟摄像头（给 Zoom/OBS 用）。
   浏览器**不提供**虚拟摄像头输出能力，PWA 做不到。
   如果"当作直播摄像头"是产品必需功能，那就必须走桌面端（Electron/Tauri + 原生插件）
   或原生 App，这会推翻技术栈决策 —— 现在还不算晚，所以先提出来。

## 8. Phase 1 结束时的已知限制

1. **没有申请麦克风权限。** 口播视频没声音等于废片，Phase 9 的录制必须带音轨，
   届时需要一起处理权限、音量与音画同步。
2. **真机测试需要 https。**
   iOS Safari 与 Android Chrome 的 `getUserMedia` 都要求安全上下文，
   `http://192.168.x.x` 这种局域网地址**不算**安全上下文，手机上会直接拿不到摄像头。
   真机测手感的可行路径：`cloudflared tunnel` / `ngrok` 开一个 https 域名，
   或本地自签证书（iOS 上要手动信任，比较折腾）。这一条建议尽早处理，
   因为"测手感"是 Phase 2 的主要工作。
3. **镜像开关目前同时决定预览与录制。** 如果将来要"预览镜像、录出不镜像"，
   只需在 Viewport 上加一个独立的 record 标志，素材侧不受影响。
4. **没有性能基线。** MediaPipe 在手机上的真实帧率、以及"追踪 + 合成 + 编码"
   三者同跑时的发热与掉帧，必须 Phase 2 实测，现在不做任何承诺。
5. **录制分辨率未定。** 建议 720p30 起步，导出分辨率作为单独选项（timeline 模型已经分辨率无关）。

## 9. 手机端适配（第二轮加入）

产品定位是手机口播，所以在进入 Phase 2 之前先把手机端的地基打好。这一轮改动的核心是
**把"成片画幅"提升为一等概念**。

### 9.1 问题：原来的实现会把手机画面裁得只剩一条

原实现让**输出画幅 = 屏幕**。手机竖屏 ≈ 1:2，摄像头流是 16:9 横屏，cover 裁切之后
只用到源画面 **26% 的横向视野**（1280px 里只用 333px）—— 人稍微一动就出画。

这是把"预览窗口"和"成片画幅"混为一谈造成的。成片比例是**发布平台定的**（抖音 9:16），
跟当前设备的屏幕长宽比没有关系。

### 9.2 解决：输出画幅（`Viewport.outputAspect`）

- 新增 `outputAspect`（默认 `9/16`，可切 `3:4` / `1:1` / `16:9` / `原相机`）；
- 输出画幅以 **letterbox** 方式居中铺在画布上，画幅之外是黑边；
- **场景坐标归一化在输出画幅上**（不是屏幕上），所以换手机、转屏幕、切画幅，
  素材的场景坐标都不变；
- 素材尺寸用 `viewport.frame`（画幅尺寸）计算，不是 `viewport.canvas`（屏幕尺寸）；
- 调试叠层会把黑边压暗并框出画幅，让"成片范围"一眼可见；
- `viewport.exportSize(1920)` → `1080×1920`，Phase 9 直接用。

验证结果（无头浏览器实测）：画幅 405×720（= 9:16），两侧各 45.5px 黑边，
切到 3:4 后可见横向范围从 405px 增至 540px，**素材场景坐标一字未变**。

### 9.3 其他手机端改动

| 项目 | 做法 | 理由 |
| --- | --- | --- |
| 页面缩放 | `maximum-scale=1, user-scalable=no` | 双指缩放要留给素材操作，不能被页面吃掉 |
| 下拉刷新 | `overscroll-behavior: none` | 拍摄中被"拉一下刷新"打断是致命的 |
| 长按菜单 | `-webkit-touch-callout: none` | 相机界面弹出"拷贝/搜索"很出戏 |
| 视口高度 | `height: 100dvh` | 地址栏收起/展开时 `vh` 不变，会露底 |
| 刘海/灵动岛 | `viewport-fit=cover` + `env(safe-area-inset-*)` | 按钮不会被 Home 指示条压住 |
| 触控目标 | 按钮 `min-height: 44px` | iOS HIG / Android 推荐的最小可点区域 |
| 工具栏 | 6 个按钮 `flex: 1 1 0` 等分，**不横向滚动** | 横向滚动的工具栏用户根本看不见后面的按钮 |
| 调试开关 | 移到右上角浮动按钮 | 给底部工具栏腾出空间 |
| 前后台切换 | `visibilitychange` 时检查 `track.readyState`，必要时重开摄像头 | 手机切后台后浏览器会暂停 video 甚至解绑轨道，不处理会「以为在拍其实没画面」 |
| 横屏提示 | 横屏窄高时浮出一句"建议竖屏使用" | 口播成片是竖屏，横着拿裁得厉害 |
| 应用图标 | `apple-mobile-web-app-capable` 等 | 加到主屏后没有地址栏，才像相机 App |

### 9.4 仍然没解决的手机端问题（诚实记录）

1. **摄像头流的方向不由我们决定。** 竖屏时浏览器通常会给竖屏流（此时 9:16 几乎不裁），
   但也可能给横屏流（此时只能裁）。`Viewport.coverScale` 就是这件事的量化指标，
   调试叠层里能看到。要不要按方向变化重开摄像头，等 Phase 2 在真机上测过再定。
2. **真机测试需要 https**（见第 8 节第 2 条），否则手机上根本拿不到摄像头。
3. 没有做方向变化自动重开摄像头、没有做 iOS 低功耗模式适配。

   检测前先降到 480p。这些是从零调参最费时间的部分。

`docs/DECISIONS.md` 第 6 节的许可证政策不变：只借鉴思路。

## 11. Phase 2：手部追踪与 pinch（本轮加入）

### 11.1 交付内容

| 模块 | 内容 |
| --- | --- |
| `hand/mediapipeHandTracker.ts` | MediaPipe Tasks Vision `HandLandmarker` 实现（全项目唯一 import `@mediapipe/*` 的地方） |
| `hand/handState.ts` | 契约扩展：`z` 分量、`HandTrackingFrame` 输入类型、21 点骨架连线常量 |
| `gesture/oneEuro.ts` | One-Euro 滤波 + 整手 21×3 关键点平滑（缺手槽位整组 reset） |
| `gesture/gestureManager.ts` | 关键点 → 掌心/速度/pinch 比例 + 迟滞 + 离散事件 + 手丢失宽限 |
| `render/debugOverlay.ts` | 手部骨架、pinch 连线与比例标签、检测耗时/输入尺寸/后端 |
| `vite.config.ts` | wasm 中间件（开发挂载 + 构建拷贝），`public/models` 加入 watch 忽略 |

### 11.2 五个刻意的设计决定

**1. 检测节奏与渲染节奏解耦。** 渲染跑满 rAF（60fps），检测按约 30fps 自己的节奏跑，
两次检测之间沿用上一份连续量。原因：一次检测要 10–30ms，每帧都检测会把渲染拖垮，
而人眼对 30fps 的手势响应完全无感。代价是必须显式管理"一次性事件"：
`gesture-start` / `gesture-end` 只投递一帧，否则 60fps 渲染会把同一次捏合触发好几遍。

**2. 降采样用等比缩放，绝不裁切。** 送进模型的帧降到 480p 高度以内，
但**不能顺手裁掉**——关键点是相对输入帧归一化的，一裁切坐标就全错。
降采样必须保持宽高比，这样归一化坐标仍然对应原始整帧。

**3. 手丢失宽限放在手势层，交互层只做兜底。**
`GestureManager.handLossGraceSeconds = 0.25s`：手整只丢了也仍然认为 pinch 按着，
只是 `pinch.center = null`（"按着但不知道在哪"），交互层看到 center 为空就把素材冻结。
超过宽限才真正结束并发出 `gesture-end`。
`InteractionManager.releaseTimeoutSeconds` 提到 0.5s，退化为"手势层整个没了"的保险丝。
分层理由：**"什么时候算松手"是手势语义，应该由手势层决定**；
与 handy 的差异（它把宽限放在交互层、4 帧）见 `handy-借鉴笔记.md` §3.2。

**4. pinch 比例在场景坐标里量。** handy 用的是原始归一化坐标，而帧坐标是各向异性的
（x 按宽归一化、y 按高归一化），斜着捏和横着捏读数会不同。
我们改用 `sceneDistance`（会按画幅比例修正 y）来算分子分母，
于是比例既**尺度无关**（手远近一致）又**各向同性**（任意方向一致）。

**5. 一个类型层面的收口。** `HandTrackingFrame` 刻意取 `CanvasImageSource` 与
`TexImageSource` 的**交集**：前者含 `SVGImageElement`（能 drawImage 但模型不收），
后者含 `ImageData`（模型能收但 drawImage 不收）。取交集后实现内部
既 drawImage 又喂模型，且全程不需要类型断言。

### 11.3 验证结果

- 单元测试 **150 个全过**（新增 30 个：One-Euro 行为 8 个、LandmarkSmoother 4 个、
  GestureManager 18 个）
- 浏览器验收 **30/30 全过**，其中 Phase 2 相关的关键项：
  - wasm 与模型均由本地同源提供（`application/wasm` / 7.46MB）
  - HandLandmarker 初始化成功，`delegate=GPU`，全程 `detectFailures=0`
  - 检测输入实测 **853×480**（源 1280×720），降采样确实生效
  - 同一时间戳重复检测不抛错（内部自增兜底）
  - 合成手喂 `GestureManager`：张开 → ratio 1.00 不触发；捏合 → ratio 0.39 触发并产出 `gesture-start`
  - **完整链路**：捏合起点命中素材 → 抓住且抓取帧不跳 → 手移动后素材位置
    **精确等于**交互层算出的目标位置 → 松开后停住并释放，
    且行为在帧内观测到恰好各一次 `grab` / `release` 变化

新增的两条"数据流"约定也因此被验证：事件只投递一帧、`transition` 只存活一帧。

### 11.4 已知限制（诚实记录）

1. **性能数字还不是真机数字。** 无头 Edge 里 `detect()` 约 25ms/帧，
   但无头环境走软件光栅（SwiftShader），这是**上界**。手机上的真实耗时、
   发热、以及"检测 + 合成 + 编码"三者同跑的掉帧情况，必须真机实测。
   调试叠层已经把 `detectMs` 与输入尺寸常显出来，就是为了在真机上一眼看到。
2. **单手 MVP。** `numHands = 1`（与 handy 一致）。`ContinuousGestures.twoHand`
   已经在收集双手中心与间距，多手分别控制素材属于需求文档第十二节。
3. **深度 z 拿到了但没用。** 单目深度太噪（handy 也明确忽略），
   契约里保留 `z` 是为了将来做"手靠近摄像头"这类手势时不用改结构。
4. **镜像下的左右手判定未验证。** MediaPipe 的 handedness 与输入是否镜像有关，
   而我们的帧没有预先镜像（镜像只在绘制时做）。Phase 2 是单手，
   handedness 不影响功能；多手时必须实测确认。
5. **模型文件 7.8MB 进了工作区**（`public/models/hand_landmarker.task`）。
   目的是离线可用；如果将来在意仓库体积，可以改成首次运行时下载 + Cache Storage 缓存。
6. **没有 Worker。** MediaPipe 仍在主线程跑。25ms 的检测在低端手机上可能拖到 20fps 以下，
   届时再考虑搬到 Web Worker（需要 OffscreenCanvas 传帧）。
   Phase 2 刻意先不做，避免在没有实测数据前把架构做复杂（需求文档第九节同此意）。

### 11.5 Phase 4 需要注意的

跟随行为（`FollowHandBehavior`）落地时，手感的三件事必须一起做，否则一定不满意：

1. **死区**：手指微动时素材不该跟着抖 —— 小于阈值的位移直接忽略。
2. **增益**：`target = anchor + (hand - anchor) * gain`，gain < 1 时素材移动幅度小于手，
   大幅移动时更容易控制；= 1 是"硬跟手"。
3. **加速/减速曲线**：手指速度变化时素材应该有轻微的惯性感，而不是瞬间启停。
   这属于 `simulate` 阶段，正好接上 Phase 10 的物理预留。

好消息是交互层已经把这些前置数据都算好了：`targetPosition`（带抓取偏移）、
`dragDelta`（每帧增量）、`cursorPosition`、以及手势层的 `palmVelocity`。
Phase 4 只需要消费它们，不需要碰手势层。

## 12. 一次真实的交付缺陷：「捏合抓不住图片」

这一节必须留着，因为它是本项目到目前为止最有价值的一条教训。

### 12.1 现象

用户报告：**可以添加图片，但捏合之后图片纹丝不动，拖不动。**

### 12.2 根因

```
grep targetPosition src/   →  只有 interactionManager.ts 在写入它，
                              src/ 里没有任何一行读取它
```

`InteractionManager` 按设计只产出 `targetPosition`（"素材该去哪"），
把"真正移动素材"留给 Behavior —— 这个分层本身是对的。
问题在于：**生产代码里唯一实现的行为是 `FIXED`，而它的 `update` 是有意为之的空实现**。
于是捏合其实**抓取成功了**（交互层 `grabbed = true`、`grabOffset`、`targetPosition` 全都正确），
但没有任何代码把这个目标位置应用到素材上。

缺失的一环是 `FollowHandBehavior`（Phase 4 的核心），而我当时把 Phase 4 留在"下一步"。

### 12.3 为什么上一轮的验证没有抓到

上一轮的浏览器验收**确实跑通了完整链路**，用的却是一个**只在验收脚本里注册的探针行为**
（`verify-drag`）：

```js
app.scene.behaviors.register('verify-drag', () => ({ ...把素材挪到 targetPosition... }));
```

也就是说，我验证的是"**链路的管道通了**"，而不是"**App 自己接上了没有**"。
脚本自己把缺失的那一环补上了，于是测试全绿、用户却用不了。

> **教训：验证"用户能看见的行为"时，测量对象必须是被交付的那个东西。**
> 从用户入口走一遍（UI → 状态 → 可见结果），而不是从中间某个接缝注入测试替身。

同类隐患还有一处被顺手发现：`attachBehaviorForMode` 对未实现的模式只是打一行 `console.info`，
而新素材默认 `mode: 'FIXED'` —— 所以"新建的图片默认不动"这件事，
在验收脚本里从来没被观察过。

### 12.4 修复

| 改动 | 内容 |
| --- | --- |
| 新增 `behaviors/followHand.ts` | `FollowHandBehavior`（`follow-hand`）：死区 + 增益 + 帧率无关的指数平滑 |
| 新增 `behaviors/modes.ts` | `registerCoreBehaviors()` + `mode → 行为` 映射表（加模式 = 加一行） |
| `behaviors/fixed.ts` | 只留 `FixedBehavior`，把 `attachBehaviorForMode` 移出去（职责单一） |
| `main.ts` | 新素材默认 `mode: 'FOLLOW_HAND'`；注册全部核心行为 |
| `debugOverlay.ts` | 新增 `grabbed` 行；被抓住的素材边框变绿并标注 `GRABBED` |

`FollowHandBehavior` 的三个参数（默认值）与理由：

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `deadZone` | 0.006 | 死区：手指微动直接忽略，否则手静止时素材会持续"呼吸" |
| `gain` | 1.0 | 增益：素材位移 = 手指位移 × gain，< 1 便于精细摆放 |
| `smoothing` | 0.03s | 指数平滑的时间常数，0 = 刚性跟手；用 `1 - exp(-dt/tau)` 保证**与帧率无关** |

两个细节值得记下来：
- **死区与增益作用在"抓取以来的累计位移"上**，而不是每帧增量。
  否则 `gain < 1` 时素材每帧只走剩余距离的一部分，会稳定在一个永远追不上的偏差上。
- **手丢失宽限期（`grabbed=true` 但 `targetPosition=null`）行为必须冻结而不是重置会话**，
  否则手回来时会以新锚点重算，表现为素材"跳"一下。

### 12.5 补的两道防线

1. **验收脚本改成测量真东西**：
   - 通过真实 UI 路径添加图片（`DataTransfer` 填 `#file-input` 再派发 `change`），
     断言新素材 `mode === 'FOLLOW_HAND'` 且 `behaviors` 含 `follow-hand`；
   - 链路测试改用**这张 UI 添加的图**，并让行为来自生产代码的挂载路径，
     脚本不再手动 `attach('follow-hand')`。
2. **调试叠层新增抓取状态**（`grabbed` 行 + 素材框绿色 `GRABBED` 标注）：
   "状态对了但画面没动"这类问题，以后一眼就能看出来是哪一层断的。

### 12.6 附带的收获

Phase 4 的核心行为其实已经落地了（死区 / 增益 / 平滑 + 15 个单测），
剩下的 Phase 4 工作是把这些参数做成可调（滑杆 + 持久化），以及加减速曲线
（那部分属于 `simulate` 阶段，接 Phase 10 的物理预留）。

## 13. Phase 9：录制（实时合成）

### 13.1 交付内容

| 模块 | 内容 |
| --- | --- |
| `recorder/mimeTypes.ts` | 按优先级探测可用录制格式 + 给人看的标签（纯函数，可单测） |
| `recorder/recorderManager.ts` | MediaRecorder 封装：状态机、分片收集、停止超时兜底、轨道清理 |
| `render/exportSurface.ts` | **离屏导出画布**：固定成片分辨率、不含黑边与调试叠层 |
| `main.ts` | 拍摄按钮（录制中显示计时）、麦克风申请、结果面板（预览 + 保存） |
| `index.html` / `styles.css` / `ui/controls.ts` | 结果面板与录制态 UI |

### 13.2 一个关键决定：录的是离屏画布，不是屏幕上那块

直接录屏幕画布会带来三个问题：letterbox 黑边会被烧进成片、分辨率随手机型号变化、
而且调试叠层（骨架/包围盒）也会进画面。

所以导出画布是**独立**的：固定 720×1280、只画摄像头帧 + 素材、不含任何调试图形。
它拥有**自己的 Viewport**（同一套源尺寸/镜像/画幅，但画布尺寸是成片尺寸），
于是 `geometry.ts` 里那套坐标换算原封不动地复用到导出画布上 ——
**素材在成片里的相对位置与屏幕上完全一致，这才是"所见即所得"的依据**。
同一份 `RenderFrame` 喂给两个渲染器，不额外拷贝。

顺带白拿了需求文档的"导出不同分辨率"：换一个 `EXPORT_HEIGHT` 就行，
素材状态一个字都不用改（场景坐标本来就与分辨率无关）。

**为什么先取 720p 而不是 1080p**：录制时手机上要同时跑
"MediaPipe 检测 + 屏幕渲染 + 导出渲染 + H.264 编码"，1080p 的每帧像素是 720p 的
2.25 倍。先用 720p 保证"能录出来"，等真机实测有余量，把常量改成 1920 就是 1080×1920。

### 13.3 格式选择：可用性优先于编码效率

候选顺序是 `mp4/H.264 → mp4/avc1 → mp4 → webm/VP9 → webm/VP8 → webm`，
理由是**能不能被用户用起来**比编码效率重要：抖音、剪映、iOS 相册对 webm 支持很差。
所有候选都不可用时**明确报错**，而不是录出一个用户打不开的文件。

无头 Edge 实测选到的是 `video/mp4;codecs=avc1` —— 说明桌面 Chrome 系也能出 mp4。

### 13.4 音频：麦克风由 main 持有，RecorderManager 只管画布轨

口播没有声音等于废片，所以录制必然要录音。两个刻意的划分：
- **麦克风在点录制时才申请**，不在页面加载时就一起要权限（那会一次索要摄像头+麦克风，用户更容易拒绝）；
- **谁创建的轨道谁负责停**：RecorderManager 只停自己用 `captureStream()` 采集的画布轨，
  麦克风轨道由 main 持有并在 `beforeunload` 时停止。否则要么录完麦克风指示灯还亮着，
  要么越权停掉调用方的轨道。

麦克风拿不到时降级为无声录制，并在状态栏说明原因。

### 13.5 验证结果

- 单元测试 **184 个全过**（新增 18 个：格式探测 7 个 + 录制状态机 11 个，
  其中"onstop 迟迟不来"用超时兜底那条是真的等了 8 秒）
- 浏览器验收 **36/36 全过**，Phase 9 相关的关键项：
  - 支持录制且选到 `video/mp4;codecs=avc1`
  - 点拍摄真的进入录制态并计时（elapsed 2.04s）
  - **录完拿到真实文件**：`video/mp4;codecs=avc1` · 720×1280 · 2.07s · 103KB · 含音频
  - 录制期间 timeline 从 0 采到 46 帧
  - 结果面板弹出，带可播放的 `blob:` 预览与 `gesturecam-<时间戳>.mp4` 下载名

### 13.6 过程中修掉的一个真 bug

`stopRecording` 开头的重入保护写成了 `if (!busyRecording) return;`，
而 `busyRecording` 只在收尾过程中为真 —— 结果是**刚开录就点停止会被直接忽略**。
验收脚本第一次跑就抓到了（`lastResult` 为 null、面板没弹），
修成 `if (!recorder.isRecording || busyRecording) return;`。

这条又一次印证第 12 节的教训：**只测内部状态机不够，要测"用户按下按钮之后拿到了什么"。**
如果只跑 recorder 的单测，这个 bug 永远不会被发现——单测里的 stop 是直接调的，
不经过 main.ts 的那层守卫。

### 13.7 已知限制

1. **录制期间的实测帧率约 23fps**（2 秒采到 46 帧），低于目标的 30fps。
   原因是同一帧要渲染两遍（屏幕 + 导出）且同时在跑 MediaPipe。
   真机数字需要实测；如果真的不够，顺序是：先降导出到 540p、再把检测降到 15fps。
2. **切到后台会丢帧。** 移动端浏览器在页面不可见时会节流 rAF，录制画面会卡住。
   目前只在状态栏提示"请保持在本页面"，没有做更严格的保护
   （例如切后台就自动停止并保存）。这条建议在真机验证后再决定怎么处理。
3. **timeline 还没有落盘。** 目前只在内存里（`scene.timeline`），
   没有"导出轨迹 JSON"或"从轨迹重新合成"的入口。需求文档第十三节的
   "拍后重新编辑对象 / 保存场景 / 场景模板"都建立在这份数据上，属于下一步。
4. **没有录制时长上限与内存保护。** MediaRecorder 是流式的（1 秒一个分片），
   但长视频（>10 分钟）在手机上是否稳定未验证。
5. **没有录制前的倒计时/预览。** 点一下就开始录，容易录进手忙脚乱的开头。

## 14. 「结果面板关不掉」——同一类错误的第三次

### 14.1 现象与根因

用户打开链接后，屏幕上直接铺着一个「录制完成」的面板挡住整个界面，
点「关闭」也没反应。

根因只有一行 CSS：

```css
.result-panel { display: flex; }   /* ← 盖过了 HTML 的 hidden 属性 */
```

HTML 的 `hidden` 属性是靠**浏览器默认样式表**里的 `display: none` 生效的，
任何作者写的 `display` 声明优先级都更高。所以面板从页面一打开就是 `display: flex`，
`hidden = true` 形同虚设；「关闭」按钮确实把 `hidden` 设回去了，
但视觉上毫无变化，用户看到的就是"关不掉"。

修复：显式补一条 `.result-panel[hidden] { display: none; }`。

### 14.2 为什么验证又没抓到（这才是重点）

验收脚本里我写的是：

```js
panelVisible: panel ? !panel.hidden : false      // 读的是"属性"
```

属性是对的，屏幕是错的 —— 测试一路绿灯。**这是同一类错误的第三次**：

| 次数 | 缺陷 | 我测了什么（代理量） | 用户遇到什么 |
| --- | --- | --- | --- |
| 1 | 捏合拖不动图片 | 脚本自己注册的探针行为把链路补上了 | 图片纹丝不动 |
| 2 | 点停止录制没反应 | RecorderManager 单测里直接调 `stop()` | 按钮点了没反应 |
| 3 | 结果面板关不掉 | `panel.hidden` 属性 | 面板盖住全屏 |

三次的共同点：**我测的是"内部状态/接口对不对"，而不是"用户看到、摸到的是什么"。**

### 14.3 落实成三条硬规矩

1. **UI 可见性一律读计算样式，不读属性。**
   验收脚本里改成 `getComputedStyle(panel).display === 'none'`；
   并且新增一条更接近"用户视角"的检查：
   `document.elementFromPoint(屏幕中心)` 命中的必须还是画布 ——
   这条能兜住**任何**意外的全屏遮挡层，不只是这一个面板。

2. **每个"用户能看到的状态"都要有一张人工过目的截图。**
   本轮开始验收脚本除了界面截图，还会把**结果面板**也截一张
   （`tools/phase9-result-panel.png`）。上一轮正因为没人看过画面才漏掉这个 bug。
   顺带这次真的看了截图，立刻又发现一处过期文案
   （底部还写着"跟随/缩放行为将在 Phase 4 / Phase 5 接入"，而跟随早已实现）——
   这本身就说明"看一眼"的性价比极高。

3. **功能验证必须从用户入口走。** （第 12 节已立，本次继续遵守：
   录制测试走的是真实的 `startRecording` / `stopRecording` / 关闭按钮，
   而不是直接调 RecorderManager。）

### 14.4 顺带确认的好消息

结果面板的截图同时证明了**离屏导出画布的设计是对的**：
预览里的成片是 9:16 竖屏、**没有 letterbox 黑边、也没有调试骨架和包围盒**，
元信息显示 `720×1280 · MP4 / H.264 · 含音频`。
"调试图形绝不会进成片"这条从设计假设变成了被看过的证据。

## 15. 真机反馈：抓取不灵敏 + 图片盖住手抓不到

用户在手机上试完给了两条反馈。两条都是真问题，但**根因完全不同**，
而且第一条暴露出我在设计上自我矛盾。

### 15.1 「图片太大时，手被盖住就抓不到」——不是识别问题

先澄清一个容易误判的点：**MediaPipe 吃的是摄像头原始帧，虚拟图片画在预览上是另一层，
它不会遮挡手部检测。** 检测从头到尾都正常。

真正断掉的是**视觉反馈回路**：素材盖住手之后，用户看不见自己的手指在哪，
自然也没法瞄准"捏在图片上"。人做这类操作靠的就是"看到手指相对目标的位置"这个闭环。

修复不是改判定，而是**把系统认为的瞄准点画出来**（`render/handOverlay.ts`）：

| 画什么 | 作用 |
| --- | --- |
| **准星**（拇指尖-食指尖中点，有无捏合都画） | "如果现在捏下去，会抓到这里" —— 图盖住手时唯一的瞄准依据 |
| **捏合连线** | 让用户确认系统认到的是哪两根手指 |
| **目标高亮**（琥珀虚线框 / 抓住后转绿） | "捏下去会抓到的是这个" |
| 比例读数 | 一眼看出"还差多少才够捏合" |

两个关键设计：
- **准星和真实抓取走同一套判定**（`InteractionManager.previewTargetId` 复用
  `findTopmostAt`），所以"提示会抓谁"和"实际抓到谁"不可能不一致。
- 这块叠层**始终开着**（不像调试叠层需要开关），因为它是操作反馈而不是调试信息；
  并且**永不进成片**（只画在屏幕画布上，导出画布是另一个渲染器）。

为此在 `ContinuousGestures` 上新增了 `pinchPoint`：拇指尖-食指尖中点，
**不捏合时也有值**。原来的 `pinch.center` 只在捏合成立时才有值
（交互层用它决定素材去哪），两者语义不同所以分开。

### 15.2 「抓取不灵敏」——我自己写的原则，我自己没遵守

`gesture/types.ts` 的类头注释里我写过：

> 离散量靠迟滞，连续量靠滤波（One-Euro）。

然后我把 pinch 的**判定比例也丢进了 One-Euro**。
后果是可量化的：`minCutoff = 1.2` 在 30fps 下每帧只走约 24%，
**每次捏合从"手指真的合上"到"系统判定成立"白白多了 100ms 以上**。
迟滞本来就是为噪声准备的，判定根本不需要被平滑拖慢。

修复：**判定比例取自未平滑的原始关键点，位置/距离仍取平滑后的**。
新增的回归测试直接把这件事钉住了：

```
单帧内从张开变成捏合就立刻触发
  → 事件立刻产出，而此时 smoothedPinchRatio 还有 0.86（远在阈值之上）
```

也就是说：如果拿平滑值判定，这一帧根本抓不住。测试里同时断言了两个数，
所以以后谁把判定改回平滑值，测试会立刻红。

### 15.3 另外三处放宽（都是"感觉抓不住"的直接来源）

| 改动 | 原来 | 现在 | 理由 |
| --- | --- | --- | --- |
| pinch 进入阈值 | 0.40 | **0.50** | handy 的 0.40 是桌面摄像头手臂距离下调的；真机上"自然捏合"常停在 0.4~0.5，用 0.40 会明显感觉抓不住 |
| pinch 退出阈值 | 0.58 | **0.70** | 迟滞带保持 0.20，握着的时候手指不会因为轻微松动掉抓 |
| 抓取宽容边距 | 6% | **8%** | 手机手指更粗；有了准星提示之后，放宽边距不会让人困惑 |

还有一个**操作习惯**上的放宽：原来只认"捏合起点必须压在素材上"
（`pinch that starts off-layer is consumed and never grabs`，抄自 handy）。
但现实里用户的动作顺序常常是"**先捏上、再把手移到图片上**"，
严格只认前者会让人强烈感觉抓不住。现在给了一个 0.7 秒的**准入窗口**：
窗口内手指移进素材就补抓；窗口过后不再补抓，避免一只长时间捏着的手划过什么就粘住什么。

### 15.4 验证

- 单元测试 **194 个全过**（新增 10 个：判定延迟回归 2 个 + 准星 4 个 + 准入窗口 3 个 + 阈值标定 1 个）
- 浏览器验收 **41/41 全过**，其中：
  - 没捏合时也给出准星、并指出"捏下去会抓到哪个素材"
  - "先捏上、再把手移到素材上"能抓住（起手在素材外不抓，移上去后抓住）
- **截图人工过目**：琥珀色准星 + 虚线目标框清晰可见，
  准星画在素材之上 —— 这次修复的核心效果是"看得见"，所以必须看图确认。

### 15.5 过程中的两个脚本自身的坑（记录以免重犯）

1. 同步连喂 40 帧手势只投递最后一帧的事件，导致交互层**从没收到 `gesture-start`**，
   准入窗口根本没开 → 误报失败。真实运行时每帧手势都配一帧场景更新，所以要交错投递。
2. 让合成手**瞬移**到素材外再捏合：One-Euro 还没跟上，
   `gesture-start` 的事件位置仍停在素材附近 → 变成"起手就在素材上"而误判。

两条都是"用合成输入模拟真实时序"时的经典陷阱：
**合成数据必须复现真实的时间结构，否则测的是脚本的时序幻想。**

## 16. Phase 5：捏合缩放 + 默认尺寸调小

> **⚠️ 本节与第 17 节的"单手捏合缩放"已被第 18 节取代。**
> 保留原文是为了留下推理链：第 16、17 节面对的现象（刚抓住就缩一下、缩放震颤）
> 和它们各自的修法都是真实的，但**根因是"单只手同时编码位置和大小"**，
> 所以最终的解不是继续调参，而是把缩放整体换成双手。第 18 节有完整推导。

用户反馈"默认图片太大（手被盖住）"，并明确"后续通过手势放大"。
两件事一起做：默认值调小 + 把缩放接上。

### 16.1 默认尺寸 0.4 → 0.28

这是口播素材相机，图片是"画中画"而不是主角。0.4 的画幅宽度在手机上已经会挡住脸和手，
真机上直接被反馈"太大"。调到 0.28 之后需要更大就用捏合手势放大。
（`DEFAULT_OBJECT_WIDTH`，改一行。）

### 16.2 缩放用"同一个捏合手势"，不新造手势

需求文档第四节 C 写的是「食指+拇指两点距离变化 → 图片缩放」。这个选择是对的：
抓取本身已经是"拇指+食指捏合"，**抓住之后继续用这两根手指开合控制大小**，
用户不需要学新动作，也不会出现"想缩放却触发了别的操作"。

实现上是新增一个独立行为 `PinchScaleBehavior`（而不是塞进 `FollowHandBehavior`）：
位置和大小是两个独立关注点，分开之后「只跟随不缩放」或「只缩放不跟随」都是一行配置。
`FOLLOW_HAND` 模式现在挂两个行为。

三个手感细节：
- **以抓取瞬间的 scale 为基准**，不是在当前 scale 上累乘（累乘会让手指停住而素材停不下来）。
- **死区 8%**：捏合比例相对抓取瞬间变化小于它时完全不动，
  否则抓取那一瞬间手指微抖，素材就会莫名其妙变大或变小。
- **上下限 0.2 ~ 4 倍**。

### 16.3 关键发现：缩放和放手指的是同一个自由度（阈值冲突）

接上缩放之后立刻撞到一个设计冲突：

> 放大素材要**张开手指**，而张开手指会让 pinch 比例升高 ——
> 一旦超过退出阈值，抓取就被判定为结束，缩放直接断掉。

用原来的 `ENTER 0.50 / EXIT 0.70` 算，从比例 0.3 抓起来最多只能放大约 **2.3 倍**，
再张开一点就掉抓。缩放基本没法用。

修法是把**退出阈值放宽到 1.00**（指尖间距 ≥ 一个掌心长度才算松手）。
语义变得很清楚：**张开手指 = 缩放，完全张开手掌 = 放手**。
参考 handy 的记录（指尖相触 0.05–0.20、张开的手远大于 1.0），
1.0 这条界线不会把"手稍微松一点"误判成放手。
副作用是迟滞带变宽到 0.5，pinch 状态比之前更稳定。

### 16.4 第二个真 bug：缩放基准用了滞后的信号

`pinchScale` 原本是「当前捏合**距离** ÷ 抓取瞬间的捏合**距离**」，两个都取自**平滑后**的关键点。
但迟滞判定已经改成用**未平滑**比例（§15.2）。两个信号延迟不一致的后果是：

> 判定在"手指刚合上"那一帧就成立并抓住，
> 但那一刻**平滑后的距离**还停在"张开"的数值附近 ——
> 于是 `startPinchDistance` 被记成一个偏大的值，
> 算出来的初始倍率明显小于 1，**素材刚被抓住就莫名缩小一下**。

修法：缩放基准改用与判定同一个低延迟信号。为此把契约里的
`PinchState.distance`（平滑距离）换成 `PinchState.ratio`（未平滑比例）：

```
pinchScale = 当前比例 / 抓取瞬间的比例     // 两者都是低延迟的，不会错位
```

顺带把契约收敛了一处：`distance` 在 `src/` 里除了喂这个计算之外没有任何消费者，
换成 `ratio` 之后没有留下"算了没人用"的字段（这类字段已经被抓过两次：
`targetPosition`、`pinchScale`）。

### 16.5 验证

- 单元测试 **207 个全过**（新增 13 个：缩放行为 11 个 + 缩放余量 1 个 + 挂载规则 1 个）
- 浏览器验收 **44/44 全过**，Phase 5 相关三项：
  - 新素材默认尺寸 **0.28**
  - **刚抓住的那一刻 scale = 1.0000、pinchScale = 1.0000**（不会先缩一下 —— 直接钉住 §16.4 那个 bug）
  - 张开手指后 **scale = 2.0000、pinchScale = 2.0000，且仍在捏合中**（不会因为张开而掉抓 —— 钉住 §16.3）

### 16.6 已知局限

1. **单手指开合时准星中点会随之移动**，缩放过程中素材可能轻微位移。
   双手张合（需求文档第十二节）没有这个问题，属于后续阶段。
2. **无法单独调整缩放灵敏度**（没有增益参数）。如果真机上觉得"张一点就放得太大"，
   加一个 `gain` 即可，位置已经留好。
3. **缩放与拖动同时生效**：捏合间距变化时位置也在跟。实际手感需要真机确认，
   如果觉得互相干扰，可以改成"距离变化超过死区时暂时冻结位置"。

## 17. 真机反馈第二轮：缩放震颤 + 录完没保存

> **⚠️ 17.1 的"单手缩放基准冻结"整套机制已被第 18 节删除**（换成双手缩放）。
> 17.2 的保存策略仍然有效，不要动。
> 17.4 的两条合成输入陷阱也仍然有效，而且第 18.5 节又踩了第六次。

### 17.1 「捏的时候图片一直放大缩小震颤」

**根因是我把原则用反了。** 第 15 节里我把 pinch 判定改成用**未平滑**的原始信号（为了低延迟），
然后顺手也让**缩放**用了同一个信号。但缩放是**连续量**，恰恰是必须滤波的那一类 ——
我在 `gesture/types.ts` 里写的原则就是"离散量靠迟滞、连续量靠滤波"，判定那半改对了，这半改反了。

后果可以算出来：缩放倍率是「当前比例 ÷ 基准比例」，而基准比例很小（≈0.3），
于是原始信号里 ±0.03 的正常手抖被放大成 **±10% 的尺寸变化**，屏幕上就是持续震颤。

**但直接把缩放改回平滑信号又会引入另一个 bug**（第 16.4 节那个）：平滑信号滞后，
抓取瞬间的平滑值还停在"张开"附近，基准会被记大，素材刚抓住就缩一下。

于是我在"基准该怎么取"上连续试错了**三版**，每一版都被真机/测试抓出问题：

| 版本 | 判据 | 怎么坏的 |
| --- | --- | --- |
| 1 | 固定预热延时 0.12s | 用户手快、在窗口内就开始张手 → 基准被刷成已张开的值，缩放永久偏掉 |
| 2 | "平滑值 ≈ 原始值"（认为滤波器追上了） | 这个条件在**缓慢合拢过程中同样成立** → 基准在手指还没合拢完就冻结（实测冻在 0.44 而不是 0.30） |
| 3 | "变化率足够小" | 缓慢合拢时平滑值的变化率（0.5/s）和静止时（0.05/s）差得不够远，阈值很难取 |
| **最终** | **两条相与**：原始比例连续 3 帧不再创新低（合拢结束）**且** 平滑变化率已很小（信号追上） | —— |

但真正让这一切成立的，是最后发现的**根本修法**：

> **给捏合比例单独一条快速滤波器。**
>
> One-Euro 的 `minCutoff = 1.2` 是为"位置不抖"调的（时间常数约 130ms）。
> 这个滞后用在位置上正好，用在控制量上就太慢了 —— 手指合拢完之后，
> 平滑值还要再花几百毫秒才追上来，于是"以当前比例为基准"总也等不到。
> **位置要平滑、控制量要低延迟，是两个不同需求，就该给两条滤波器。**
> 现在捏合比例走 `minCutoff = 8`（时间常数约 20ms），追上得快，
> 基准能冻结在**真实的捏合值**（实测 0.3020，而合拢结束时的真值是 0.30）。

这一条是可以复用的经验：**同一个信号要同时服务于"离散判定"和"连续量"时，
不要在"用不用滤波"之间二选一，而是按各自的延迟需求配两条滤波。**

改完之后实测：基准 0.3020、张开手指得到 1.99 倍、全程不掉抓，
"刚抓住时"的尺寸变化 ≤ 4%（滤波尾部的必然残差，肉眼不可见）。

### 17.2 「视频录完好像没有保存」

**根因是产品语义，不是代码 bug**：**"下载"和"存进相册"在手机上不是一件事。**

| 环境 | 点 `<a download>` 的结果 |
| --- | --- |
| iOS Safari | **不进相册**，只落到"文件"App 里 —— 用户翻不到就会认为"没保存" |
| Android Chrome | 进"下载"目录，也不进相册 |
| 桌面浏览器 | 静默落到默认下载目录，没有任何提示 |

所以改成**按设备能力选最合适的保存方式**（`src/ui/resultSaver.ts`，纯逻辑可单测）：

| 优先级 | 方式 | 触发条件 | 用户得到什么 |
| --- | --- | --- | --- |
| 1 | **系统分享面板**（`navigator.share({ files })`） | 支持 `canShare({files})` | 面板里有「存储到照片」，**这是网页把视频放进手机相册的唯一路径** |
| 2 | **另存为对话框**（`showSaveFilePicker`） | 桌面 Chrome / Edge | 用户自己选位置，比静默下载清楚 |
| 3 | 普通下载 | 兜底 | 明确告知"在下载目录里，**不是相册**" |

配套的三件事：
- 按钮文案随方式变化：「保存到相册」/「另存为…」/「保存视频」，**不再用会让人误解的"保存视频"**；
- 面板上常驻一行提示，说清楚点下去会发生什么、东西会去哪；
- 另留一个「下载」按钮作为永远可用的备选（分享面板失败/取消时用户有出路）；
- 用户在分享面板里取消 → 提示"已取消"，**不弹红字**（取消不是错误）。

### 17.3 验证

- 单元测试 **224 个全过**（新增 12 个：保存策略 9 个 + 缩放基准 3 个）
- 浏览器验收 **45/45 全过**，其中：
  - 抓住后张开手指 → 倍率 1.99、尺寸收敛到 1.97，**全程仍在捏合中**（不会因为张开放手）
  - 刚抓住那一刻尺寸变化 ≤ 4%
  - 保存按钮的文案与所选方式一致，且提示文案非空
  - 新增内部诊断出口 `interactionManager.scaleDebug`
    （`armed` / `reference` / `minRaw` / `settleFrames`）——
    缩放"什么时候才开始生效"是这里最容易出问题的地方，暴露出来才不用靠猜

### 17.4 合成输入陷阱（第四次与第五次）

两处验证脚本自身的问题，都值得记：

1. **一次性投递静态状态会骗过"信号收敛"判据。**
   我原来"同步喂 40 帧再一次性 setGestureOverride"，等于把同一个手势状态重复投递很多帧，
   平滑滤波器的收敛过程根本没发生 → `smoothedRatio` 与 `rawRatio` 一起瞬移。
   改成**逐帧驱动**（每帧一次 `gestures.update` + 一次投递）才复现真实时序。
2. **每帧等两个 rAF 会制造假平台期。**
   同一个状态被渲染循环投递两次，变化率出现 0 → 又骗过了"信号稳定"判据。
   改成**一次 rAF 一帧**。

累计五次同类问题，规律已经很清楚：
**合成数据必须复现真实的时间结构（每帧一次、单调推进、不重复投递），
否则测的是脚本的时序幻想，而不是产品的行为。**

## 18. 真机反馈第三轮：「不好操控」→ 缩放改成双手

### 18.1 先把反馈翻译成几何问题

用户的反馈是"用起来还是很奇怪、不好操控"，并且自己给出了方向：**能不能识别两只手，用两手操控缩放。**

这个方向是对的，而且第 16、17 节的两轮修补之所以反复，根因就在这里：

> **单只手的捏合同时编码了两个自由度。**
> 拇指尖与食指尖的**中点**是位置，两者**距离**是大小。
> 用户想只改大小，但手指的运动学做不到 —— 一开合，中点必然跟着漂；手一抖，两个量一起变。

再加上信噪比：单手捏合间距只有约 **0.03 个画幅宽**，
One-Euro 滤波后残余抖动仍在 ±0.003 量级 —— **相对噪声 10%**。
第 17 节那三版"基准冻结"判据，本质上都是在跟这个 10% 较劲。

双手把两个自由度真正解耦，而且两手间距约 **0.4 个画幅宽**，
同样的绝对噪声除以大一个数量级的基准，**相对误差小十倍**。
于是那套脆弱的冻结逻辑可以整段删掉 —— 这是"改对结构"比"调参"省事得多的典型例子。

### 18.2 改动清单

| 层 | 改动 |
| --- | --- |
| 追踪 | `numHands: 2`（MediaPipe 上限） |
| 手势层 | `maxHands: 2`；每只手一个独立的迟滞门；`pinches[]` 数组；`twoHand = {active, center, distance}`（**两只手都在捏合**才成立） |
| 交互层 | 删掉整套单手缩放机制；新增"双手会话"：第二只手加入时记下 `startDistance` 与素材相对两手中点的偏移 |
| 行为层 | `PinchScaleBehavior` → `TwoHandScaleBehavior`（类型 `two-hand-scale`），基准取会话开始时的 scale，死区 5%，τ 50ms |
| 界面 | 准星叠层画**每只手的**捏合连线；双手成立时画一条虚线**缩放宽轴**并标出倍率；状态栏与调试面板显示 `2/2 手捏合`、间距、倍率 |

单手模式的语义保持不变：**拖动永远是"抓着它的那只手"在拖，单手绝不改尺寸。**

同时定下两条**会话归属**规则（都是双手带来的新情况，缺一个用起来就会怪）：

1. **后来的手不抢会话。** 两只手通常都捏在**同一张图**上，如果后捏的那只手把抓取会话抢过去，
   素材会在两只手之间反复易主（"刚才还跟着我的右手，怎么突然跟左手了"）。
   所以：目标素材已经被抓着 → 这次 pinch 只是"加入同一次操作"，会话仍属于先抓住的那只手。
2. **只有一个素材被抓住时，双手缩放才生效。** 两手间距是一个**全局**量：
   如果两只手各抓了一张图，两张图会跟着同一个中点、按同一个倍率动，于是叠在一起。
   退化成"各拖各的"是唯一可预测的语义。

### 18.3 顺带挖出来的三个真 bug（都由新写的端到端测试钉住）

改双手的过程中，`tests/twoHandFlow.test.ts`（用与真机同构的视口：16:9 摄像头 + 9:16 画幅 + 镜像，
每一层都用真实实现）立刻抓出三个问题。它们**在单手下不会暴露**，是"第二只手一捏上"才会触发的：

1. **抓取被莫名释放（图片掉了）。**
   根因：**捏合状态按槽位排，抓取会话按左右手记账**，而槽位会因第二只手出现而对调
   （两只手到旧锚点的距离可能几乎相等，对称站姿正好是平局）。
   对调之后，抓着手的那只手在新槽位里"第一次"触发 pinch，于是又发一次 `gesture-start`；
   交互层把它当成新抓取，先 `release(hand)` 释放掉正在进行的会话，
   而这次的新位置又不在素材上 → 图片掉了。
   三处修复：槽位认领**先按左右手标签**（比"离上一帧最近"更稳的身份信号）；
   **同一只手的重复 start 直接忽略**（这只手从头到尾没松过）；
   光标改为**跟着抓着素材的那只手**（`PinchState` 加上 `handedness` 字段）。
2. **第二只手一捏上，图片自己变大/变小。**
   根因：基准间距取在**滤波器追赶的途中**。一只手刚出现在新槽位时，
   滤波器可能还带着另一只手的陈旧状态，要花约 0.4 秒滑过去，而基准正好在这段时间被采样。
   修法是在滤波器里加一条**"跳变 = 重新捕获"**判据：手腕在 33ms 内位移超过整帧的 1/4
   （`REACQUIRE_JUMP`）就整组重置。手不可能这么快，所以这一定是重新捕获而不是真实运动。
3. **光标取成另一只手**（素材瞬间跳到另一只手下面）—— 同 1 的第三处修复。

这三个 bug 有一个共同的教训值得写下来：

> **"哪只手是哪只手"必须有一条稳定的身份链。**
> 只要有一个环节用"第几个"代替"哪只手"（槽位号、数组下标、第一个捏合槽位），
> 第二只手一出现就会错位。现在这条链是：MediaPipe 标签 → 槽位认领 → `PinchState.handedness`
> → `grabbedBy`，每一层都用标签做身份。

  `twoHandFlow` 端到端（2 个）、槽位稳定性（含镜像视口）、跳变重置（2 个）、

  - 第二只手捏上 → 手数 2、捏合手数 2、倍率 1.0000、scale 1.0000

### 18.5 合成输入陷阱（第六次）

截图脚本第一版是**同步**喂帧的（`feed()` 不等 rAF），于是 `setGestureOverride` 里

结果"手明明捏上了，素材却没被抓住"，截图里的 `grabbed` 是空的。
截图断言（`grabbed === true && 倍率 ≈ 2`）当场把它抓出来了 ——

4. 追踪两只手时 MediaPipe 的推理开销翻倍，**真机帧率还没测**（调试面板的

## 19. 手势文法：「捏合＝鼠标左键，握拳＝Esc」

用户提出：手势必须有明确的文法，否则"识别到的手势"和"用户想做的事"会长期对不上。
核心约定是**拇指+食指捏合 = 鼠标左键**，并且给出了三条规则：

1. 只有拇食指捏合才触发抓取（别的动作都不选择）
2. 握拳取消一切选定动作
3. 一只手选中素材时，另一只手也捏合 → 两手分开放大、靠近缩小

规格写在 `docs/手势文法.md`（先写规格再写代码），本节记录实现里的关键决策与踩到的坑。

### 19.1 第二个维度不能用"其余三指是否伸展"，要用"食→中夹角"

第一版方案（我提的）是：**捏合 = 拇食指靠近 且 中指/无名指/小指伸展**。
用户指出更合适的做法：**参考中指与食指的夹角**。这个方案明显更好，理由是一条几何事实：

> θ 是**相对量**。握拳时食指与中指**一起**蜷曲，共同项被抵消，所以 θ 仍然很小；
> 而捏合时食指屈向拇指、中指保持朝前，θ 明显变大（实测 40° 对 5°）。

| 姿势 | 食指向量 | 中指向量 | θ |
| --- | --- | --- | --- |
| 张开 | 朝前 | 朝前 | 小（≈6°） |
| **握拳** | 卷向掌心 | 卷向掌心 | **小**（≈5°） |
| **捏合** | 屈向拇指 | 朝前 | **大**（≈40°） |

**⚠️ 参考系绝对不能用"手掌轴线"（手腕→中指 MCP）**：握拳时食指卷向掌心，
相对手掌轴线会变成一个**大**角度，就和捏合混在一起了。必须用**中指自己的朝向**做参考。
这条已写进代码注释和规格文档，因为它是整个方案成立的前提。

顺带一个好处：**"捏合要求三指伸展"这条有风险的硬条件被去掉了**。
真人捏合时无名指与小指常常自然半蜷，那条硬条件会拒判掉一批正常用户；
现在手指蜷曲度**只**用于握拳检测。捏合的判定改成：

```
gap < ENTER  且  (食指伸展  或  θ > ENTER)
```

两个条件用"或"：食指屈向拇指的常规捏靠 θ，拇指去碰伸直食指的"直捏"靠伸展度 ——
任一成立即可，两种常见捏法都不会被拒判。

### 19.2 手型是静态判定，动作是手型的组合

这条把整套逻辑理顺了：

| 层 | 内容 |
| --- | --- |
| 手型（静态，带迟滞） | `FIST` > `PINCH` > `OPEN` > `OTHER`，按优先级顺序判定 |
| 动作（状态机） | `IDLE` →（PINCH）`GRABBING` →（另一只手也 PINCH）`SCALING`，任何取消条件回 `IDLE` |

优先级的意义：**握拳是急停，任何时候都优先**。即使某只手同时"像捏合"（拇食指很近、
夹角也大），只要四指蜷曲就按握拳处理。

### 19.3 实现时改了规格的三处（规格里已标注）

1. **`OPEN` 的取消是按手的，不是全局的。**
   规格原文写"任一只手 `OPEN` → 取消"。实现时发现这条**会让双手缩放根本无法进行**：
   两手操作时，没在捏合的那只手**本来就是张开的**，每次都把正在进行的操作清掉。
   改成：只有**抓着素材的那只手**张开才算放手。用户在选项里选的"保留张开手掌作为
   第二种取消方式"因此仍然成立，只是作用域是"这一只手"。
   急停（`FIST`）保持全局 —— 它是刻意动作，不需要关心是哪只手。
2. **`FIST`/`OPEN` 做成状态，不做成离散事件。**
   原计划新增 `gesture-start/fist` 事件。改成状态（`controls.fistHands` / `pinches[].shape`）：
   取消是"此刻有没有手握拳"，用状态表达天然幂等；**事件一旦被合并/丢失，急停就失效了** ——
   而"合成输入被覆盖导致事件丢失"这个坑在本项目已经踩过六次（§17.4 / §18.5）。
3. **手型量取自原始关键点，不带快滤波。**
   试过给控制量单独配一条快滤波（第 17 节的老设计），但它会把"张开→捏合"这种大跳变
   拖上 2 帧，**破坏"单帧就抓住"这条真机验证过的性质**。抖动改由 gap 迟滞 +
   `FIST`/`OPEN` 的 2 帧最短保持吸收。顺带把 `controlSmoother` 整个删了 ——
   单手缩放已经移除，它没有消费者了，留着就是每帧白算两遍 21 个关键点。

### 19.4 实现中发现的一个真 bug：双手缩放的基准被滤波滞后污染

写端到端测试的时候发现的，而且**在上一轮的实现里一直存在**：

> 双手缩放的基准间距取自**平滑后**的捏合中点。
> 但"张开 → 捏合"这个动作本身会让**捏合中点移动约 3–4% 掌长**
> （两指从分开到接触，中点跟着走），而平滑值要 ~2τ（约 0.26 秒）才追到位。
> 基准正好在这段时间被采样 → **素材在第二只手捏上时自己变大 6%**，
> 然后稳定在这个偏大的尺寸上（不是抖动，是永久偏移）。

这正是第 18.3 节"基准取在滤波追赶途中"那个坑的**另一个入口**：
上一轮只堵住了"手整只瞬移"（`REACQUIRE_JUMP`），没堵住"同一只手改变姿势"。

修法有原则性：**基准必须用无滞后的测量**。
`TwoHandState` 因此给两份间距 ——

| 字段 | 来源 | 用途 |
| --- | --- | --- |
| `distance` | 平滑后的捏合中点 | 实时倍率（要稳） |
| `rawDistance` | **原始**捏合中点 | **基准**（要准） |

两边在静止时收敛到同一个物理量，所以倍率精确落在 1；运动时留一点滞后，
那只是手感上的阻尼（用户感知为"跟手但不飘"）。

端到端测试里也踩了同一类坑的第七个变体：**合成输入必须把时间喂够**。
12 帧（0.4s ≈ 3τ）还剩 5% 残差，大到足以让"回到 1 倍"这条断言失败；
改成 24–30 帧后才稳定。

### 19.6 真机反馈：两个问题，三个缺陷

文法实现完上真机，用户报了两个问题：

> 1. "当我选中后握拳，想要再次选中的时候，总是把我识别成握拳，但实际上我已经张开手了。"
> 2. "屏幕里同时有两个手时，如果一只手握拳，自动识别为无法选取，容易干扰另一个手的抓取。"

第 2 条是我设计上的取舍错误（下面 19.6.1）。第 1 条查下来是**两个**独立缺陷叠加（19.6.2 / 19.6.3）。

#### 19.6.1 `FIST` 不该是全局的（问题 2）

第一版照规格实现成"任意一只手握拳 → 清空一切"，而且我在规格里就写下了这个风险
（"另一只手只是随意搭着、若被判成握拳"），当时选择"急停优先"。
真机证明代价不可接受：那一只手把另一只手的操作清掉了。

改成**每只手管自己的会话**：

| 情况 | 行为 |
| --- | --- |
| 抓着素材的那只手握拳 | 取消**它自己**的会话 |
| 什么都没抓着的手握拳 | **什么都不做**（连"待重新武装"都不设） |
| 两只手各抓一张，其中一只握拳 | 只松开那一张 |

急停的能力没丢：抓着素材的手一握拳就停。要停两只手就两只手都握拳。

#### 19.6.2 握拳判据要求"四指全蜷"，而深层捏合时无名指小指本来就会蜷进掌心（问题 1 之一）

捏得紧的时候，无名指与小指会自然蜷向掌心 —— 那不是握拳，是捏。
而握拳的优先级高于捏合，于是这个姿势被读成握拳，用户"选中之后再也选不中"。

修法：**握拳只认食指 + 中指深蜷**。理由是**中指才是诚实的信号**：
捏合根本不用中指，所以"中指深蜷"就等于"这只手没有在做捏合"；
无名指与小指太容易跟着姿势漂，不该参与判定。

#### 19.6.3 手离开画面后，槽位里留着上一次的手型（问题 1 之二，最隐蔽）

`updateSlotWithoutHand` 第一版是这样写的：

```ts
if (slot.shape !== 'pinch') { slot.center = null; return; }   // ← 就在这里丢了状态
```

对非 pinch 的手型直接 return，**从不把手型改回 `other`**。
于是"某只手曾经是握拳、然后离开画面"之后，`controls.pinches[].shape` 一直是 `fist`。
而交互层的"重新武装"是拿这份手型判断的 —— 它的门槛就永远解不开了。

真机表现正是用户描述的那句："我已经张开手了，它还说我是握拳"。

修法有原则性：**手型是对"这一帧看到了什么"的描述**，看不到就是 `other`；
"捏合会话还按着"是**另一件事**，拆成独立字段 `pinchHeld`：

| 字段 | 含义 | 手离开画面时 |
| --- | --- | --- |
| `shape` | 这一帧看到的手型 | 立刻 `other` |
| `active`（来自 `pinchHeld`） | 捏合会话是否按住（宽限期内为真） | 宽限期内仍 `true`、`center = null` |

这条缺陷能被抓到，靠的是验收脚本里**两只手交替进出**的场景：
脚本从 11.6 到 11.8 共享同一个 `GestureManager`，11.7 留下的左手槽位
把 11.8 的重新武装锁住了。也就是说 —— 如果没有"端到端"这一层，它会一路带到用户手里。

顺带加了一道**安全阀**：重新武装最多拦 1.5 秒，到点无条件放行。
手型判定万一卡住，"再也抓不住任何东西"比"多等一秒"严重得多。

#### 19.6.4 一个被自己的测试推翻的假设（值得记）

我一开始认定问题 1 的成因是**透视缩短**（手指朝向镜头时平面距离塌缩），
并且还为它写了实现（含深度的三维距离）。写测试时才发现：

> **平面比值本身对透视缩短几乎不敏感** —— 指尖与掌根是**一起**塌缩的。

测试当场把这个假设否掉了（我原本写的断言"2D 伸展度应小于 1.35"直接失败）。
真凶是 19.6.2 与 19.6.3。三维距离作为**第二道门**保留了下来
（手掌长度估计一旦异常、比值会整体漂移，两把尺子同时说蜷曲才允许判握拳），
但它不是当初以为的那个作用 —— 这一点在代码注释与规格 §1.1.2 里都改成了实话。

**教训**：不要用"想当然的机制"直接去写修法，先用一个测试把机制验证出来。
这次的顺序恰好对（先写测试再改），所以只损失了一点时间而不是留下一个错误的实现。

- 单元测试 **275 个全过**（17 个文件）
- 浏览器验收 **61/61 全过**，新增三项针对本次真机反馈：
  深层捏合不判握拳、放松手不判握拳、旁观的手握拳不干扰另一只手的抓取
- 回归测试覆盖三条缺陷，每条都对着真机现象写（见 `docs/手势文法.md` §8.2）

## 20. 录制健壮性 + 指弹删除（Phase 8 落地）

真机上的手势已经能用了，于是下一个真实考验变成"**录一条完整的口播视频**"。
按"会不会毁掉一次录制"排序，这一轮做了三件事。

### 20.1 Phase 8 终于落地：`boundaryMode` 从"只存不执行"变成真的

`state.boundaryMode` 这个字段从 Phase 1 就存在，但**没有任何行为读它** ——
`constrain` 阶段一直是空的。后果是真机上很实在的一条：

> 手一滑把素材拖出成片画幅，它就飘在 letterbox 暗区里：命中测试算得到、
> 用户却很难瞄准，实际体验就是"素材丢了，只能清空重来"。

现在由 `BoundaryBehavior` 在 `constrain` 阶段统一收口。三个设计点：

1. **放在 `constrain`，不是塞进每个行为里。** 跟手、双手缩放、将来的物理都跑在它**前面**，
   只有最后一步统一约束，才不会有哪条路径把素材漏出去。这也是这个阶段从 Phase 1 预留的原因。
2. **约束要按缩放后的真实外框算**，而且三件事都得对：缩放参与、**纹理宽高比参与纵向**
   （画面的宽与高单位不同）、旋转参与（旋转在像素空间做，所以先在"各向同性场景坐标"里转）。
   少算任何一项，"约束住了"就是错觉。
3. **一条兜底：任何模式下只要外框与画幅完全没有交集，就拉回中心。**
   理论上前面的钳制已经保证了这一点，但这条把"素材彻底丢失"从"不可能"变成"结构上不可能"——
   它也是我自己写错钳制数学时的安全网。

顺带定了五个模式的分工：`CENTER_CLAMP`（默认，锚点在画幅内）/`FULL_VISIBLE`（整个素材在里面）/
`ALLOW_OVERFLOW`（至少露 15%）/`NO_BOUNDARY`（不约束，预留给"扔出画面"这类玩法），
`CLAMP` 与 `CENTER_CLAMP` 合并（语义重叠，不留没人用的分支）。

### 20.2 指弹删除：用户提的方案比我的好

"怎么删掉一张图"我先想了三个方案：**拖出画幅即删除**（❌ 和边界约束直接打架：
拖到边缘到底是"放到边上"还是"删除"分不清）、**双手同时握拳**（❌ 和急停语义打架：
急停时双手一起握拳就把图删了）、**三指捏合**（⚠️ 符合文法但深捏时中指本来就靠近拇指，有误判风险）、
**垃圾桶区**（✅ 但要在屏幕上常驻一块区域）。

用户提出**指弹**（食指勾住再弹出）。这个方案明显更好，两个理由：

1. **它是过程，不是姿势。** 静态手型只有那么几个（捏合/握拳/张开），每一个都已经有明确含义，
   再塞一个进去就开始互相打架；而"从勾到弹"**不占用任何静态手型**。
2. **它天生带方向与速度。** 这正是删除（选目标）和物理（冲量）都需要的信息 ——
   同一次检测在编辑态里是"把这张图弹掉"，在 Phase 10 里就是"给这个物体一个冲量"。

实现里最关键的一条是 **`gap ≥ minGap`（装填态要求拇指在旁边）**：

> 松开捏合时食指也会从蜷曲变伸展，看起来和指弹一模一样。
> 区分靠拇指 —— 捏合时拇指就贴在食指上，所以**"从捏合里松开"永远凑不出装填态**。

（这条门槛的具体数值在 §21.1 被真机反馈改过一次：它该等于**捏合退出阈值**，而不是我拍的那个数。）

删除是破坏性操作，所以配了 **2 秒淡出期**：弹中之后素材半透明淡出、留在原地，
**期间再捏住它就等于撤销**，时间到才真正移除。不做"弹中即消失"——录到一半误弹一次就只能重新加图。

分工也值得记：交互层管"这次删除还算不算数"（撤销、超时），`flick-fade` 行为管"看起来怎么样"
（改不透明度，并且**记住原值、撤销时还原**），**Scene 管真正移除**（对象树归它）。
三个模块各管一段，所以端到端测试是必须的 —— 单测各自绿不代表合起来对
（第一版测试就忘了挂行为，素材"啪一下消失"而不是淡出）。

### 20.3 录制上限：把"录到一半崩掉"这个可能性去掉

MediaRecorder 是把整段视频**攒在内存里**的（分片也是 Blob）。手机上录几分钟 720p 就是几百 MB。
没有上限、也没有预警，最坏情况是录到一半页面崩掉、**前面全丢**。

现在有两条护栏（哪个先到算哪个）：**时长 5 分钟**、**体积 400MB**（≈9 分钟 @6Mbps，
码率异常时兜底）。到上限**不是错误**：自动停止、照常出片，然后明确告诉用户为什么停了。
80% 起状态栏与录制按钮变色预警，让用户有机会主动收尾。

另外一条同样属于"别毁掉这次录制"：**页面切到后台时自动停录并保存**。
后台时 rAF 停止、导出画布不再重绘，继续录只会得到一段**冻结的画面**（而声音还在走，
越差越远），内存还照样涨。停下来至少把已经录到的部分完整交给用户 ——
比"回来发现录了个残废文件"好得多。

### 20.4 验收里又踩到两个坑（都是"脚本自己骗自己"）

1. **把"帧数"当时间用。** 淡出期是 2 秒，我在验收脚本里喂了 90 帧就断言"到期" ——
   但 rAF 一帧只有约 16ms，90 帧才 1.44 秒，**根本没过期**。
   产品的 `dt` 走真实时间，合成输入也必须按**真实时间**喂够。
   （这是第七、第八次同类问题了：合成输入必须复现真实的时间结构。）
2. **状态栏被覆盖。** "已到录制上限"的提示写在 `stopRecording()` **之前**，
   而它自己会写一条"录制完成"，于是提示被吃掉。
   断言"状态栏要说明原因"当场抓到。改成在停止完成之后写。

另外顺手清掉一个小坑：验收脚本是**破坏性**的（指弹会把素材真的删掉），
所以给它加了个开发用后门 `createDemoObject()`，让破坏性用例造一个**自己的**素材 ——
否则后面截图的用例会"找不到素材"，而且截图里会留着上一条状态栏消息
（`setStatus` 后门就是为还原状态加的）。

## 21. 真机反馈第四轮：指弹「勾住了却一直不触发」

用户的反馈只有一句：**"食指钩住的条件是什么？为什么我一直没有触发。"**

这句话本身就是最重要的信息 —— 它是**用户没有办法自己回答的问题**。
指弹是唯一一个"做对了也没有任何反馈"的手势：捏合有准星、握拳有横幅，
而勾住食指在屏幕上什么都不会发生，直到它弹出成功。所以这一轮真正的交付物
不是一个新阈值，而是**让"为什么没装填"变成可读的数字**。

### 21.1 先承认门槛定错了（两条都错）

| 门槛 | 原值 | 现值 | 为什么错 |
| --- | --- | --- | --- |
| `loadedIndexReach` | `1.20` | `1.35` | 1.20 要求的是"折回掌心"的真拳头级别，而指弹只要**指节弯下来的半勾**，读数约 1.2–1.35 —— 正好被挡在门外 |
| `minGap` | `0.80` | `0.60` | 语义错位：这条想说的本来就是"这只手**没有在做捏合**"，而捏合退出阈值是 `0.60`。自然的指弹姿势是**拇指压在食指/中指上**（像打响指），那时 gap 常常只有 0.5–0.8 ⇒ **一次都装填不上** |

两条都放宽之后必须补回"别把别的手势吃进来"，于是**新增**第三条
`minMiddleReach = 1.10`（装填时中指不能深蜷）：

- 它和**握拳阈值（蜷曲 `≤1.10`）是同一个数**，于是**握拳与装填天然互斥** ——
  用户"松开拳头"的动作不会再被读成一次指弹；
- 它把"整只手半蜷/放松"也排除了。

并把 `minReachGain` 从 `0.30` 放到 `0.25`、`releaseIndexReach` 从 `1.55` 提到 `1.60`（与装填留出可测增量）。

**这里有一个刻意的取舍**：装填那三条只是"这只手没在做别的事"的**粗筛**，
防误触的主力是**速度 ≥1.5 + 3 帧窗口 + 伸展增量 ≥0.25**。
之所以敢往灵敏那一侧偏，是因为删除有 **2 秒后悔期**（捏住即撤销）——
误弹一次是可恢复的，而"永远弹不出来"是不可恢复的。

### 21.2 让"勾了为什么不装填"变成数字

调试叠层新增 `flick` 两行（读数 + 判定，达标 `+`、没达标 `-`）：

```
flick      right open · 食 1.30+ · gap 0.70+ · 中 1.60+ · 装填 12/2
           弹速 0.00-需≥1.50 · 已装填
```

第二行只报**当前挡路的那一条**（"食指需≤1.35" / "拇指需离远" / "中指别蜷"），
比把三条门槛都列一遍短得多，也直接回答了"我该改哪个动作"。

**另外补了一个观测项：峰值瞬时速度。** 触发判定用的是窗口内**平均速度**，
而人感受到的是**某一帧的瞬时速度** —— 两者差得不小，用户会一直以为自己弹得够快。
所以面板给的是**装填期间的峰值**，标定就变成"我现在的读数 vs 门槛"这一件具体的事。

### 21.3 一个真 bug：读数可能取自错的那只手

原来 `debug.flick` 固定取 `primarySlot()`，而它**优先给捏合中的那只手**。
双手同时在画面里时，用户实际勾住的那只手常常不是 primary ⇒
**面板读数纹丝不动**，看起来就像"程序完全没看到我勾手指"。
改成优先取**正在装填的那只手**（`flickDebugSlot()`），没有装填的才退回 primary。
这条有单测钉住（一只捏着 + 一只勾住，读数必须来自勾住的那只）。

### 21.4 人工过目截图又抓到两个界面缺陷

这一轮的价值再次证明"断言绿了不等于东西能用"——两张调试面板截图一看就露馅：

1. **面板被画布右边缘切掉。** 手机竖屏画布宽约 500px，而我把三条门槛全写进一行
   （`食指 1.30✓需≤1.35 · gap 0.70✓需≥0.60 · 中指 1.60✓需≥1.10 · 装填 12/2`），
   于是**最该读的数字恰好在屏幕外**。两处修正：只写读数 + 只报挡路的那一条；
   面板按可用宽度**自适应缩字号**（下限 8px），长行不再溢出。
2. **`✓` / `✗` 渲染成豆腐块。** 等宽字体栈里没有这两个字形（无头 Edge 和真机都一样）。
   标记改用 ASCII 的 `+` / `-`。

### 21.5 验证

- 单元测试 **337 个全过**（20 个文件）。`flick` 新增"装填门槛（真机标定）"5 条，
  `gestureManager` 新增"指弹调试读数"3 条（含 §21.3 的取手 bug）
- 浏览器验收 **76/76 全过**，新增 5 项：合成"半勾"能装填、"握拳"不装填且面板指出挡路的那一条、
  面板给出了读数与门槛、两张标定截图；合成输入用的是 `indexReach 1.3 / gap 0.7 / middleReach 0.85`，
  正好落在**旧门槛必失败、新门槛必成功**的位置
- 人工过目：`tools/flick-arm-half-hook.png`（`食 1.30+ gap 0.70+ 中 1.60+ 装填`）、
  `tools/flick-arm-fist.png`（`中 1.00-` 且提示"中指别蜷(≥1.10)"）

### 21.6 仍然诚实的未知

- **真机手感还没验。** 上面所有数字都来自合成手；`1.35 / 0.60 / 1.1` 是否覆盖真实人群的
  "半勾"分布，只能靠用户带着面板报读数来定。这正是 §21.2 存在的理由。
- **速度门槛（1.5）是最可疑的一个。** 30fps 下一次指弹只跨 2–3 帧，平均速度会被稀释；
  如果真机上用户普遍"姿势对了但弹速不够"，下一步不是降门槛，而是改成**用峰值瞬时速度**
  来触发（面板已经在测这个量了，等真机数据决定）。

### 21.7 真机标定开始前的拦路 bug：弹速读数恒为 0.00

第五轮真机标定还没开始，先发现 §21.2 那两行读数里**最该读的那个数根本读不出来**。

- **现象**：调试面板第二行永远显示 `弹速 0.00-需≥1.50`，不管弹得多快。
- **根因**：`peakTipSpeed` 的 getter 写成 `loadedFrames > 0 ? peakSpeed : 0`。
  而峰值**恰恰出现在"弹出去的那一帧"**，那一帧走完 `loaded = false` 就把
  `loadedFrames` 清零 —— 刚采到的峰值被 getter 自己抹掉了。
  单测实测：一帧内食指伸展 1.0→1.8、指尖走 0.12，真实瞬时速度 **3.6**，面板读数 **0.00**。
- **为什么 §21.5 的验证没抓到**：浏览器验收只断言 `typeof peakSpeed === 'number'`
  —— `0` 也是 number；而合成手的"装填"姿态指尖是**静止**的，峰值本来就是 0，
  所以"读数是 0"在合成输入下看起来完全正常。**断言绿了不等于东西能用**，又是一次。
- **修复**：读数改成**保持**上一次的峰值 —— 勾住时它是本次实时峰值，弹完保持不动
  供人抬眼读数，下次开始装填时清零，手丢了也清零。3 条单测钉住（`tests/flick.test.ts`）。

这条卡住的正是 §21.6 里被点名"最可疑"的速度门槛：下一步要不要把触发判定从
**窗口平均速度**改成**峰值瞬时速度**，本来就得靠真机读数来定 —— 而那个读数当时是看不见的。
所以真机标定的第一步不是报数字，是**先让数字能读出来**。

## 22. 工程效率：省 token 的工作规矩

起因是用户发现**这个项目的 token 消耗明显比其他项目快**，问我的工作流程是什么。

量出来的主因不是"这个项目特别费"，而是**会话太长**：本会话的 transcript 压缩后 7.72 MB，
而另一个会话只有 146 KB。Agent 每一轮都要把完整历史重发一次，所以

```
总消耗 ≈ 轮数 × 平均上下文长度
```

历史随轮数线性增长 ⇒ 总消耗是**平方级**的。"越到后面越贵"是这个结构的必然结果。

但次因是**我自己的行为**，而且我在解释这件事的那一轮里又亲手演示了一遍：
为了算清 token 花在哪，我写了 14 个一次性诊断脚本、猜错三次 `.jsonl.zstd` 的帧格式、
反复二分定位一个"其实是我自己写错的扫描器"报出来的语法错误。全部无功而返。
**答案一直就在上下文里**（这个会话已经有 4 轮真机反馈、2 次 checkpoint），
我根本不需要去挖 transcript。

### 22.1 六条硬规矩（后续会话必须遵守）

| # | 规矩 | 为什么 |
| --- | --- | --- |
| 1 | **验证分级**：小改动只跑 `tsc --noEmit` + **相关**测试文件；`vitest run` 全量只在"改动了公共模块"时跑；`node tools/verify-browser.mjs`（4 分钟、76 项）**一个任务只跑一次**，放在最后 | 浏览器验收里 90% 的检查与本次改动无关，但它每跑一次都要按当时的臃肿上下文重新付费 |

## 23. 第五轮真机反馈：指弹模型整个推翻（"弹脑瓜"）

用户的反馈附带了一张调试叠层截图：

> "并非打响指，就是**弹脑瓜**的那个动作……其他手指不动，食指蓄力弹出"

截图里的 `flick` 两行：`食 1.52- · gap 0.45- · 中 0.91- · 装填 0/2`，外加 `pinch 0.449 ACTIVE`。

### 23.1 前四轮都在调数字，但错的是**动作**

| 轮次 | 做法 | 结果 |
| --- | --- | --- |
| 第一版 | 食指 ≤1.20 / gap ≥0.80 | 一次都装填不上 |
| 第四轮 | 放宽到 ≤1.35 / ≥0.60，并加 `middleReach ≥1.10` | **还是**一次都装填不上 |
| 第五轮 | 承认模型错了，重写 | —— |

真机三条读数**全不达标**，其中 `gap` 那条**方向和真实动作相反**：
弹脑瓜的蓄力是**拇指扣在食指尖上**（gap 0.45），而门槛要求 `gap ≥ 0.60`（拇指躲开）。
那三条描述的是一个**不存在的姿势** —— 所以再放宽也没用。

这一轮最重要的判断依据不是读数本身，而是**"三条全不达标"这个形状**：
一条不达标是标定问题；**三条全不达标、其中一条方向还相反，就是模型问题**。
第四轮把三条各放宽一点点却没动方向，注定还要失败一次。

### 23.2 更贵的一处：装填姿势**就是捏合**，于是还有第二道锁

截图里的 `pinch 0.449 ACTIVE` 才是真正致命的：蓄力姿势触发了捏合判定
（pinch 立即生效，没有 hold），于是**对着目标图蓄力必然先把图抓起来**；
而 `interactionManager` 里有一句"正抓着东西的那只手弹一下没有意义"会 `continue` 跳过指弹。
那句话的理由写得很清楚 —— "**装填态要求拇指不参与**，已经挡住了捏合" ——
正是 §21.1 那条错门槛的**配对**。前提错了，两条一起废。

**教训**：放宽一条门槛时，要连带检查**依赖它成立的那些"因此不必处理"的短路逻辑**。
`if (grabbing) continue` 是"因为不会有这种情况，所以不写"的典型 ——
这种代码在前提失效时不会报错，只会静默地永远不触发。

### 23.3 改了什么

- `flick.ts` **重写**：装填 = 拇指扣住（`gap ≤0.65`）+ 其余三指蜷着（`middleReach ≤1.10`），
  **不看食指**；弹出 = `gap` 增量 ≥0.25 + 指尖速度 ≥0.8，且其余三指仍蜷着。
  新增 `releasing` 阶段 —— 真机 20fps 下常常"拇指先松一帧、食指下一帧才飞出去"，
  只在脱离那一帧判会漏掉真正快的那一帧。
- `interactionManager.ts`：删除目标改成**这只手抓着的那张**（没抓着才回落到指尖下最上层）。
- `debugOverlay.ts`：两行改成"**扣住** / **甩开**"，`食` 挪到第二行且**不带达标标记**（纯观测）。
- `docs/手势文法.md` §3 阈值表 / §8.5 / §9.1 同步重写。

### 23.4 顺手修掉的那个"读数读不出来"（见 §21.7）

上一轮加的弹速读数**恒为 0.00**：峰值恰恰出现在甩开那一帧，而 getter 用
`loadedFrames > 0 ? peak : 0` 把读数抹掉了。这次真机截图里 `弹速 0.55`（非 0），

## 24. 第六轮真机反馈：两个"手感"问题 + 一次代码审计

用户的反馈很短：**"拖动的时候有时候会突然松掉"**、**"一个手捏的时候有时候会放大变小"**。

### 24.1 「拖动时突然松掉」—— 找到一个真 bug，已修

`pinch → other` 的手型切换是**即时**的（`handShape.ts` 里只有 `fist`/`open` 需要连续帧），
所以只要有一帧判成 `other`（半开、关键点噪声），`updateSlotWithHand` 就**当帧**发出
`gesture-end`，而 `interactionManager.ts:335` 收到就 `release()` —— **图当场掉**。

**不对称才是问题所在**：整只手丢了有 `handLossGraceSeconds = 0.25s` 宽限，
而"捏合这一项判丢一帧"的宽限是 **0**。真机 20fps（一帧 50ms）下单帧噪声很常见。

修法：`PINCH_RELEASE_GRACE_FRAMES = 3` —— 连续 3 帧判成 `other` 才算真的松手；
宽限期内继续算"按着"，并**保留上一帧的 `center`**（清空会让交互层按"按着但不知道在哪"
把素材冻结 100ms，拖动会一顿一顿）。

**刻意只对 `other` 生效**：`fist` 是急停必须立刻停（它另有 `fistHands` 通道），
`open` 是主动的"张开手掌＝释放"且自己已有 2 帧保持。
第一版把宽限套到了**所有**非 pinch 上，结果 3 个既有测试红了 —— 那 3 个测试守的正是
"急停要立刻"和"张开手掌要立刻"，**它们是对的，错的是我那一版**。收窄之后全绿。

### 24.2 「单手捏着会放大变小」—— **没定位，不猜**

代码上要触发双手缩放，必须 `readTwoHand` 里**两个槽位都判成 `pinch` 且都有 `center`**；
空槽位的 `shape` 被强制成 `other`，所以**一只可见的手不可能**触发它。
⇒ 真机上那一刻，镜头里**必须存在第二个"手心"**（用户的另一只手，或者 MediaPipe
把同一只手检出了两次）。

⇒ 这需要一次观察，判据在调试叠层上（下一节），**不靠猜**。

**观察方法**：出现"放大变小"时看那两行 ——
`hand N hand(s)`、`pinch ... k/2 手捏合`、`two-hand off/on`、`grabbed`。
如果是 `2 hand(s)` + `two-hand on`，那就确认是第二只手/幽灵检测；
如果只有一个 `1 hand(s)` 而 `two-hand on`，那说明是**同一个槽位被喂了两次**，是另一类 bug。

### 24.3 审计发现的三处 —— 两处修了，第三处退回

| # | 位置 | 结论 |
| --- | --- | --- |
| 1 | `readTwoHand` 没有最小间距保护 | ✅ **已修** |
| 2 | `assignSlots` 标签翻转会换槽 | ✅ **已修** |
| 3 | 紧捏可能被判成握拳 → 急停 → 松手 | ❌ **试了两种改法，都退回** |

**#1 两手最小间距**：两个捏合中点几乎重合时（同一只手被检出两次、或两手叠在一起），
`distance / start` 的基准接近 0，子像素抖动会被放大成剧烈缩放（交互层 clamp 到 0.1–10，
也就是允许抖出 10 倍）。加了"两手中点至少隔开 **1 个掌长**"才认双手；
`rawDistance`（缩放基准）也过同一把尺子，太小就退回平滑值。用掌长当尺子，与手的大小无关。

**#2 槽位连续性**：`handedness` 不会因为手走了就清空，所以 slot1 会一直"记得"自己是 `left`。
这时只要右手被 MediaPipe 的标签翻一次，第一轮认领就会把它塞进 slot1 —— slot0 于是"手丢了"，
而"正在抓着哪张图"正绑在 slot0 上，接着就是 0.25s 后放手。
补了一条**很克制**的修补：只有"认领它的槽位上一帧是空的"**且**"另一个槽位上一帧有手、
现在空着、离这只手足够近"同时成立时才把它搬回去（也就是"手没怎么动，是标签变了"）。
**标签优先的既定顺序没动。**

**#3 退回的理由**（这条值得记）：它不是 bug，是**刻意的优先级** ——
"同时像捏合又像握拳时，握拳优先（急停优先于选中）"，`handShape.test.ts:136` 专门钉着。
两种改法都被既有设计挡回来：

- 加"食→中夹角大就不算握拳" —— 直接推翻那条优先级（**10 个测试红**）。
  而且真握拳时中指深蜷 → MCP→TIP 向量很短 → 夹角本来就不可靠，
  拿它当否决条件等于**在最该急停的时候把急停关掉**。
- 把 `pinch -> fist` 的保持帧数从 2 提到 4（想靠去抖挡住连续误判）——
  撞上"握拳/张开要连续 2 帧"这条既有约定（**3 个测试红**，含握拳急停的端到端），
  还把急停从 100ms 拖到 200ms。

**更要紧的是它大概不是真凶**：捏合时食指是伸着的（本项目实测 ≈1.5），
要变成握拳得蜷到 ≤1.10 —— 那不是"一帧抖动"，是真的换了姿势。
**所以这条保持原样，等真机数据。**

### 24.4 验证

- `tsc --noEmit` 干净；单测 **347 个全过**（新增 3 条：松手去抖、双手最小间距、槽位连续性）
- **回归测试做过反向验证**：把 #2 的修补关掉，对应测试确实变红（`expected 1 to be +0`），
  打开就绿 —— 否则就是"脚本自己骗自己"（这个坑本项目踩过 6 次）。
  ⚠️ 顺带记一个坑：我第一版用"把阈值调成 0 / -1"来关它，两次都没关掉 ——
  `0` 让"距离恰好为 0（合成手逐帧完全一样）"照样满足条件，而 `-1` 被**平方**成了 +1 反而更宽松。
  **要关就直接关那段逻辑，别去调参数。**
- **没有跑浏览器验收**（按 §22 一个任务只跑一次，这一轮已用在指弹那边）。
  ⚠️ 它里面有拖动/释放类断言，理论上会被"松手最多晚 2 帧"影响，需要时补跑。

### 25.3 验收抓到的两个失败（值得记）

跑浏览器验收时红了 2 条，**一条是我上一轮埋的回归**：

1. **letterbox 颜色检查红了** —— 它写死了旧底色的 rgb 阈值（`b <= 28`），而新品牌底色是
   `#1A1A1D` = (26,26,29)，**差 1**。改成"很暗且接近中性"的判据：
   这条检查真正想说的是"画幅外是背景、不是画面内容"，用"暗+中性"表达才对得上意图
   （摄像头测试图是绿色 (0,136,0)，照样分得开）。**教训：与主题无关的检查里写死主题值，
   主题一改它就红 —— 而且看起来像是主题改错了。**
2. **双手缩放截图倍率红**（2.0 → 1.4175）—— 这是 §24.3 那个"两手最小间距"门槛的副作用，
   而 §24 那轮我**没有跑浏览器**，所以没暴露。原因很直接：验收脚本里
   "两手相距 **0.09**、再拉到 0.18 = 正好 2 倍"用的是**自然起手间距**，
   而我把门槛设成了 1 个掌长 ≈ **0.10** —— 正好压在它上面，基准被推迟到拉开之后才取。
   改成 **0.35 掌长（≈0.035）**：比自然间距小 2.5 倍留足余量，
   而"同一只手被检出两次"那种幽灵重合远小于它，照样挡得住。已加单测钉住"0.09 必须算双手"。

**教训**：给"防幽灵"设计门槛时，**先量一下正常姿势落在哪**，别凭"看起来很小"下手；
门槛压在正常姿势上，症状是"功能变弱"（倍率少一半）而不是"报错"，最难发现。

### 25.4 验证

`tsc --noEmit` 干净；单测 **348 个全过**；浏览器验收 **76/76**（两次跑：第一次 74/76 抓出上面两条，
修完复跑 76/76）。`dist/` 已重建。

## 26. 素材箱（第一版：数据层 + 面板）

§25 定的流程是"工具箱式"：拍摄前先挑素材，口播中用手势让它们出现。
这一轮先落**数据层 + 面板**，**不动"拍摄前先进素材箱"这个强制入口** ——
因为素材现在还不会"出现/隐藏"，把它做成必经一步就只是白白多一次点击。

### 26.1 三层概念（"别写死"就落在这里）

| 层 | 是什么 | 谁持有 |
| --- | --- | --- |
| 资源 Asset | 解码出来的东西（位图，将来的视频元素） | `core/assets/assetManager` |
| **素材 Material** | 用户"这次要用"的那一件（箱子里的一格） | **`core/material/library.ts`（新）** |
| 对象 SceneObject | 摆在画面上、被手势操控的那一份 | `core/scene/objectManager` |

资源/对象分离本来就有（同一素材可摆多份），素材层补的是"用户挑了什么"。
`Material.objectId` 记下"这件素材对应画面上哪一份" —— 将来"手势让素材出现/隐藏"靠它找回。
真要"同一素材摆多份"时把这个字段换成数组即可，调用方只经过 `link` / `remove` 两个口子。

### 26.2 加一种新素材**只改一处**

`MATERIAL_KINDS` 是唯一出处：名字、短标、说明、`implemented` 全写在那里；
UI 的按钮和"以后支持"那行提示都从它读。

**没做完的种类 `implemented: false`，而且不变成按钮** ——
不做"点了没反应"的假按钮，它们只在界面上列成"以后支持：文字 / 视频 / 动图 / 贴纸"。
单测钉住"这一轮只有图片是真的能用"：做新种类时改那一行，**别去 UI 里加 `if (kind === ...)`**。

### 26.3 界面

- 底栏「＋」改成**打开素材箱**（以前是直接拉文件选择器），加素材走箱子里的「添加图片」。
  多这一步是有意的：箱子是"这次要用的东西"的清单，加素材只是它的一种操作。
- 每行：缩略图（没有位图的种类显示短标，不留空白框）+ 文件名 + 种类说明 + 删除。
- 删素材会**把它在画面上的那一份一起收掉** —— 否则会出现"箱子里没有、画面上还在"的鬼影，
  而且那一份还会继续响应手势。
- 素材箱与设置面板**互斥**：同时开着会互相压住，谁在上面取决于 DOM 顺序，很难解释。

⚠️ 文件名用 `textContent` 写而不是 `innerHTML` —— 文件名是用户给的，不能让它注入标签。

### 26.4 验证

- `tsc --noEmit` 干净；单测 **358 个全过**（新增 `materialLibrary.test.ts` 10 条）；浏览器验收 **76/76**
- ⚠️ 改「＋」的行为之前先确认过：验收脚本**不点「＋」**（它直接往 `#file-input` 喂文件），
  所以这次改动不影响那 76 项。**改 UI 入口前先查脚本怎么驱动它**，否则会白红一批。

### 26.5 下一步

1. 素材箱成为**拍摄前的入口**（要跟"手势让素材出现/隐藏"一起做，否则素材摆不出来）
2. 按 `implemented` 逐个补种类：文字 → 动图 / 贴纸 → 视频
3. 打包（Capacitor 工程 + 存相册插件 + 离线资源）—— 等用户装好 JDK + Android SDK

## 27. 素材抽屉（"拉窗帘"）—— 手势方案定稿 + 实现

方案是**用户自己想的**，我做的是"改一处 + 挡两个坑 + 定权责"。

### 27.1 定稿：从顶边把素材"拉"下来

> 在画面上方约 1/5 处**捏合**、往下拖 → 抽屉跟手拉下来 →
> 每一格是个**开关**：捏一下显示、再捏一下收起（**可以同时显示多张**）。

用户原话是"张开手掌 → 抓紧 → 往下拉"。**方向对、隐喻很好**（拉的过程本身看得见，
用户不用记新姿势、做错了也看得出来），但"抓紧"必须改成**捏合**：

- 这个项目里 **握拳 = 急停**（优先级最高）——"抓紧往下拉"那一下会先把急停触发掉，
  手里正抓着的素材会被松掉；
- 而**捏合在没有素材的地方起手，现在本来就是什么都不做的**（交互层有"抓取准入"），
  所以这个姿势是**空着的**，拿来开抽屉正合适。

### 27.2 两个必须挡住的抢姿势（都会真的发生）

1. **拉到底松手那一帧可能被读成指弹**：`gap` 由小变大 + 指尖正在快速移动，
   指弹的两个条件可能同时成立 ⇒ **拉/推的过程中屏蔽指弹**（`suppressFlick`）。
   反过来说：拉的过程中手型不变、`gap` 几乎不变，所以正常拉动**不会**误删 ——
   这正好旁证了指弹当初把"甩开增量"当主力判据是对的。
2. **抓取准入窗口会抢**：交互层允许"起手后 0.7s 内移进素材也算抓住"，而拉抽屉**必然经过素材** ⇒
   抽屉盖住的那块区域里，**一个事件都不给场景**。

### 27.3 用**位置**分权，而不是"抽屉开着就什么都不许干"

- 捏合起手在**拉手条带**（画面顶边 20%）→ 拉下 / 推上；
- 起手在**抽屉盖住的区域之内、但不在这条带里** → 点某一格；
- 在抽屉**下面** → 完全是正常场景操作（抓素材、拖动、缩放）。

所以"抽屉开着就不能抓素材"是**错的**：只有被抽屉盖住的那块归它。
两块区域的判定都走**真实布局**（`getBoundingClientRect` / `elementFromPoint`），
不在 JS 里另抄一份高度 —— 抄一份就会和样式表对不上，而"这块区域归谁"决定着手势会不会打架。

### 27.4 状态只有一个来源

"这件素材现在显示着没有"读的是**画面对象自己的 `visible`**，抽屉不另存一份状态 ——
两份迟早不同步，而"抽屉说显示中、画面上却没有"是最难查的那一类。

### 27.5 验证

`tsc --noEmit` 干净；单测 **372 个全过**（新增 `drawerPull.test.ts` 14 条）；浏览器验收 **76/76**。
`dist/` 已重建。

新增的那 14 条里，有两类是这个项目的"老病"：
· 在条带之外捏合**必须完全不理会**（不许抢正常的抓取）；
· 拉的过程中**必须屏蔽指弹**（不许"拉个抽屉把图删了"）。

### 27.6 还没做 / 待真机调

- **手感参数全是估的**：拉手条带高度 `0.2`、拉满距离 `0.3`、松手保持阈值 `0.45`、
  推回关闭距离 `0.1`。等真机试完再调（都在 `drawerPull.ts` 的 `DEFAULT_DRAWER_PULL_CONFIG`）。
- 抽屉里的**顺序/分组**，以及"这次拍摄要用的"和"临时加的"要不要分开。
- 抽屉成为**拍摄前的必经入口**（§25 的流程）。
  现在 `＋` 加进来的素材**默认就是显示着的**，所以第一次用抽屉多半要"先收起、再放出"；
  等入口做了，从素材箱挑进来的应该**默认藏着**，那才符合"拍摄时才放出来"。

### 27.7 真机反馈后改的：抽屉里**直接铺图片**，不做列表行

第一版抽屉用的是和素材箱一样的**列表行**（缩略图 + 文件名 + "显示中/已收起"）。
用户真机反馈：**"图片是横行的…很难选中"**。

改了两处：

1. **内容改成图片网格**（`.drawer-tile`，4:3 长方形，直接铺图，`object-fit: cover`）。
   没显示的压暗、显示中的加主色描边 + 角标。理由是**手指要指得中**，
   而且"这是哪张图"一眼就该看出来，不该靠读文件名。
2. **允许点偏**：`drawerMaterialAt` 先按点到的元素判，**点空了就找最近的一格**（48px 内），
   距离按**点到矩形**算（点落在格子里为 0），所以点在两格之间的缝里也能归到最近那格。
   这一条才是针对"很难选中"的：捏合中点是拇食指的中点，**天然会偏**。

⚠️ 这一轮同时给验收加了**两条**（76 → 78 项）：一条走真实链路
（合成手 → GestureManager → 抽屉判定 → DOM）验证"顶边捏合往下拖能拉下来、
且里面是图片格子而不是列表行"，一条产出人工过目截图 `tools/drawer.png`。
**"抽屉开了"和"抽屉能用"是两件事** —— 上一版就是开了但没法点，
所以断言里连格子数一起看。

## 28. 方向再改：抽屉换成"打响指翻页"（流畅是最重要的）

用户试用后的反馈：**"感觉使用起来还是不流畅。我觉得流畅是最重要的。"**
并自己提了新方案：**提前选好图片和顺序 → 打响指按顺序出图；图固定出现在左上角；不要抽屉了。**

### 28.1 先诊断"为什么不流畅"（这一步比换手势更重要）

原来那条路（顶边捏合往下拉 → 再在某一格上捏一下）要求三件事**同时**成立：

1. **起手位置要对**（捏合必须起手压在素材上 / 在拉手条带里 / 落在某一格上）
2. **动作要分几段**（捏上 → 拖 → 松手 → 再捏）
3. **手得一直在画面里、还得保持住**

任何一件没做到，用户的感觉就是"没反应 / 选不中"。再叠上真机 20fps、平滑、去抖的天然延迟。

> **结论：这不是调参能救的 —— "瞄准 + 多段动作"本身就是慢的。**

### 28.2 新方案（用户提的，比我的好）

| | |
| --- | --- |
| 拍摄前 | 素材箱里**排好顺序**（不再需要逐张摆位置） |
| 拍摄中 | **打响指**（拇指 + 中指贴住再弹开）= 下一张 |
| 位置 | 图默认出现在**左上角**；**拖过就记住**，翻回来还在你放的地方 |
| 回退 | **不要**（只能往后；打到底循环） |
| 抽屉 | 从主路径**摘掉**（代码先留着，不做可见入口 —— 项目没有 git，删了就真没了） |
| 拖动 | **保留** —— 用户明确说"拖动是我的特色" |

它好在哪：打响指**不用瞄准、单段动作**；而"图固定出现在左上角"把**最后一处瞄准也去掉了**。
拍摄中一个需要瞄准的动作都不剩。

### 28.3 为什么技术上风险低

打响指和**指弹（删除）是同构的**：都是"拇指贴住某根手指 → 急速弹开"，
只是指弹贴**食指**、打响指贴**中指**。所以判定直接复用指弹那套状态机
（装填 → 弹开窗口 → 增量 + 指尖速度），**不用发明新姿势、不用重新摸一套标定**。

落成 `src/core/gesture/snap.ts` + `tests/snap.test.ts`（12 条）。

**故意先复制一份、而不是合并进 `flick.ts`**：合并就要动已经真机标定过、
被 23 条单测钉住的代码。等打响指真机验证过，再把两者合成"以手指为参数"的检测器。

**防撞的关键一条**：装填要求"拇指到**中指**的距离 **小于** 拇指到**食指**的距离" ——
否则普通捏合（拇指贴食指、中指在附近）也会被算成打响指。
两条手势从此按**哪根手指**分开：**指弹用食指（删除）、响指用中指（翻页）**，互不干扰。

### 28.4 尚未验证的风险（只有真机知道）

- **20fps vs 响指速度**：一次响指可能整个发生在两帧之间。判定看的是"贴住 → 弹开"两帧的变化，
  理论上不怕，但**这是唯一必须真机验的点**。
- **和握拳的边界**：打响指时中指是蜷的，若食指也蜷到判据里就会变成握拳（急停）。
- **响指有声音，会被录进去** —— 用户已确认"没关系，就这样"。

### 28.5 下一步（要动的地方）

1. `handShape.ts` 补一个"拇指 → 中指"的距离读数（现在只有拇指 → 食指）
2. `gestureManager.ts` 每槽加一个 `SnapDetector`，事件挂进 `GestureState`
   （⚠️ 会动到 `GestureState` 类型，几处测试/验收里的字面量构造要跟着改）
3. 调试叠层：**把中指的读数做进面板**（与指弹那两行并列）—— 真机一轮就能标定完
4. 主流程：素材默认**藏着** → 响指 → 下一张出现在左上角（拖过的记住位置）
5. 抽屉：摘掉入口

### 28.6 接线（第二轮）与踩到的坑

接线落在：`handShape.ts` 补"拇指→中指"的 `middleGap`；`gestureManager.ts` 每槽一个
`SnapDetector`、事件进 `GestureState.snaps`；`main.ts` 消费 `snaps` 翻页；
调试叠层加一行 `snap` 读数（真机标定靠它）；抽屉从 `main.ts` 的运行时路径**摘掉**
（`drawerPull.ts` / DOM / CSS / 单测都留着，等"跳到第 N 张"的需求回来再用）。

**两个必须记的坑：**

1. **`GestureState` 加一个必填字段，会连锁改 7 处字面量构造**（2 处在 `main.ts`，
   5 处在测试里）。这是**故意的**：让编译器把每一处都点出来，比"可选字段悄悄不填"安全。
2. ⚠️ **"素材默认藏着"把验收脚本一次打红 16 条**，症状全是 `grabbed=false`，
   看着像"抓取坏了"，其实只是**那个对象没显示**（脚本后面几十条检查都在用它）。
   修法是让脚本按新流程走：**加完素材先响指翻出来，再继续后面的检查**。
   **教训：改了"东西什么时候出现在画面上"，等于改了所有后续检查的前置条件** ——
   这类改动要预期"红一大片"，别一条条去查。

### 28.7 验证

`tsc --noEmit` 干净；单测 **384 个全过**（新增 `snap.test.ts` 12 条）；
浏览器验收 **79/79**（新增"新素材默认藏着 + 翻一次出来落在左上角"、
"拖走之后位置记得住"，并产出人工过目截图 `tools/drawer.png`）。

**"位置记得住"这条断言是刻意设计成能抓到 bug 的**：它先 `setVisible(false)` 再翻回来 ——
这正是"有多张素材时上一张被收起来"的真实状态。
第一版实现拿"当前是否显示"判断要不要摆到左上角，于是**拖过的图翻回来会被重置**；
这条断言能把它抓出来（单纯"翻一次"抓不到，因为那时它本来就可见）。

### 28.8 还没做

- 素材箱里的**排序界面**（现在顺序 = 加入顺序）
- 抽屉降级成"跳到第 N 张"（代码还在，没入口）
- 打包（等用户装 JDK + Android SDK）

### 28.9 真机第一次读数：速度门槛 0.8 → 0.4

接线之后的第一条真机反馈：**"速度不够，0.8 太高了"**，要求降到 0.4 —— 已改
（`DEFAULT_SNAP_CONFIG.minTipSpeed`）。

**只改这一个数。** 一次动两个变量，下一次读数就解释不清是哪个起的作用 ——
标定必须一次一个。

**为什么敢比删除（指弹，也是 0.8）低**：代价不对称。
翻页翻错 = 再打一下翻过去，**零损失**；删除删错 = 图没了。
所以"**翻页灵敏、删除保守**"是有意为之，单测里钉成**不变式**
（`snap.test.ts`：`snap.minTipSpeed < flick.minTipSpeed`）—— 以后有人手一滑把两个调成一样，
这条会红。

**下一步看什么**：还是面板那一行 `snap`。
如果 0.4 还打不响，那就**不是速度问题**，而是"贴住"这一步没被认出来 ——
看 `中` 那个数贴住时有没有降到 0.65 以下、`装` 有没有到 `2/2`。
那时要改的是 `loadedMaxGap`，**别再动速度**。

### 28.10 真机第二条读数：门槛太松 → 0.65 收到 0.50

用户："**有点太灵敏了，无论食指还是中指，很多时候没有和拇指贴住也能触发。**"

根因是"贴住"的判据太松：`loadedMaxGap` 原来是 **0.65** —— 那是我给"关键点抖动"留的余量，
结果松到**根本没贴上**也算装填，随手一晃就翻页 / 删图。

改成 **0.50**（两个手势一起改）：

- 0.50 **正好等于捏合的进入阈值**，语义干净："**真的贴上了才认**"；
- 真机蓄力实测是 **0.45**，所以还留着 0.05 的余量，不至于"贴上了反而认不出"；
- **两个手势共用同一个数**：它们是同一个物理量。分开写迟早漂开，
  而"翻页认得出、删除认不出"这种不一致最难查 —— 单测里钉着两者相等。

**又一次"一次只改一个数"**：上一轮改速度（0.8→0.4），这一轮改距离（0.65→0.50）。
两轮之间你能明确说出"哪一条不对" —— 这就是分开改的价值；一起改就说不清了。

### 28.11 如果还是不对，下一个旋钮

- 贴上了却**触发不了** → 0.50 对这只手太严（个体差异），回调到 **0.55**；
- 贴上了**还是误触发** → 问题不在距离，而在**缺少"贴住并保持"这个动作**：
  该动的是 `loadedFrames`（现在 2 帧），**不要再压距离**。
  压到 0.45 以下会开始出现"真贴上了却认不出"，那比误触发更难用。

### 28.12 真机第三、四条读数：两个门槛用**两点法**一次定标

用户报"**贴着拇指移动也会触发换页**"，并自己猜"该用拇指和中指的**相对速度**"。
**猜的方向对，机制不对** —— 我核了代码：

- 判定里的 `速` 确实是**中指指尖相对画面**的绝对速度 —— 用户看对了；
- 但触发**还要求** `增 ≥0.25`（拇指↔中指要真的分开），所以"贴着一起移动"**理论上不该触发**；
- **实际会触发**，是因为手一动快、关键点就糊，**距离读数自己会跳 0.2~0.3** ——
  "分开了"那一关被**跟踪噪声**满足了，而速度那关因为整只手在动轻松通过。
  **两道关被同一个噪声源同时喂饱：看着独立，其实相关。**
- 用户提的"相对速度"就是 `增 ÷ 时间`，和 `增` **是同一个信息**，单独换掉解决不了问题。

**真机给了两组数，一次定标：**

| 动作 | `增` | `速` |
| --- | --- | --- |
| 贴着拇指移动（**误触发**） | 0.3 | 0.6 |
| 真打响指 | 0.6 | 3.0 |

速度差 **5 倍** —— 它才是主力判据。门槛卡在两点中间：

- `minGapGain` 0.25 → **0.45**
- `minTipSpeed` 0.4 → **1.2**

**两个一起改是有依据的**：两组数**都量到了**，不是猜的。
（"一次只改一个"针对的是**没有两组数据**的情况。）

**顺带纠正一个我自己写错的不变式**：上一轮我在单测里钉了
"翻页门槛必须低于删除，因为翻页误触发没成本"。**那是错的** ——
两个动作的自然速度不一样（响指比食指弹出快得多），两个门槛本来就没有可比性。
它还在这一轮**直接把我挡住过一次**（1.2 > 0.8 让断言红了）。
**错的"不变式"比没有不变式更糟**，已换成"门槛必须卡在实测两点之间"。

**还查了删除那边**：指弹的速度门槛本来就是 **0.8**，而这次量到的误触发是 **0.6** ——
**已经挡得住**，所以没动它。但它的**增量门槛 0.25 同样低于误触发读数 0.3**，
原理上是一道无效的关；等真机给出**食指**那边的两点读数再一起定
（**别拿中指的数去推食指**）。

## 30. 上传到 GitHub（以及这条路上的几个坑）

仓库：**`waitandstudy/gesturecam`（私有）**。换号过程见 §30.4。

第一个提交 `4f4a874`：95 个文件、25778 行；第二个 `0ce297f` 是这份文档。

### 30.1 两个坑（下次别再踩）

1. **`git push` 必须走代理。**
   这台机器 `git config --global http.proxy = http://127.0.0.1:65532`（本地代理）。
   - 直连 GitHub **能连上**（`ls-remote` 一个公共仓库成功），但**传大文件会被重置**：
     `error: RPC failed; curl 55 Send failure: Connection was reset` —— 9MB 传到一半断。
   - **走代理就成功了**（顺手把 `http.postBuffer` 提到 512MB）。
   - ⚠️ 那个代理**不是一直在跑**：第一次尝试报的是
     `Failed to connect to github.com port 443 via 127.0.0.1` —— 代理当时没开。
     **推送失败先看一眼代理在不在**：`Test-NetConnection 127.0.0.1 -Port 65532`。
2. **凭据库里有一条垃圾条目。**
   `git credential fill` 按 `host=github.com` 拿到的第一条，用户名写着「你的新Token」，
   长度 40、**已失效（401）**。显式带上 `username=2458283786-blip` 才拿到能用的那条。
   **推代码 / 调 API 都显式带用户名**，别让 git 自己挑。

### 30.2 推送用的方式（不落盘、不打印）

不把 token 写进 `.git/config`，也不打印它 —— 每次推送在同一条命令里现取现用：

```
git -c http.postBuffer=524288000 -c credential.helper= \
    -c "http.extraheader=AUTHORIZATION: basic <base64(用户名:token)>" push origin main
```

`credential.helper=` 置空是为了**绕开图形化凭据弹窗**（在非交互环境里它会一直等）。

### 30.3 关于仓库内容

`.gitignore` 早就有（`node_modules` / `dist` / `tools/bin` / `*.exe` 都排除）。
仓库里唯一的大文件是 `public/models/hand_landmarker.task` **7.46MB** ——
**离线要用，必须进库**（整个仓库约 9MB，远低于 GitHub 的单文件 100MB 上限）。

### 30.4 换账号：怎么把仓库挪到另一个 GitHub 号

最初建在了 `2458283786-blip` 下（用凭据管理器里缓存的 token 建的）。
用户要求换成另一个号，最终落在 **`waitandstudy/gesturecam`**。

**关键的一条认知**（用户问过"我网页版已经登录了，不能推上去吗"）：

> **浏览器登录 ≠ 终端能推。**
> 浏览器用的是 **cookie**；`git push` 用的是**凭据管理器里的 token** ——
> 两套**完全不共享**。所以"网页登着"对命令行没有任何帮助。

但**浏览器登录确实用得上** —— 走 OAuth 那一步就行：

1. **在网页上建一个空仓库**（**不要**勾 "Add a README" —— 勾了会多一个提交，推送时得先合并）；
2. `git remote set-url origin https://github.com/<新号>/<仓库>.git`；
3. **直接 `git push`** —— git 发现没凭据 → 凭据管理器走浏览器授权 →
   用**浏览器里登着的那个号**签发凭据（这次甚至没来得及弹窗就过了）。

**换号不需要重建本地仓库**：提交都在本地，换个远端地址重推即可。

提交身份也一并改到新号 —— **只改这个仓库，不动全局配置**：

```
git config user.name  "waitandstudy"
git config user.email "2454252994@qq.com"
```

⚠️ 已有的两个提交**作者仍然是旧的**（改配置只影响之后的提交）。要改写历史得再强推一次。

### 23.7 浏览器验收抓到的真 bug：手离开画面时指弹检测器不重置

`updateSlotWithoutHand` 里重置了手型（`slot.shape = 'other'`），但**没有碰 `flickDetector`**。
检测器的装填状态与起跳参考帧都建立在"这一帧看到了这只手"上 ——
它本来就有 `update(null, dt)` 的"手丢了"分支，**但生产代码里没有任何地方喂过 null**，
于是那个分支一直是**死代码**。

后果：手一离开画面，装填状态就**永远停在"已扣住"**，调试面板挂着上一次的读数骗人。
这正是 §21.2 专门做那两行面板要避免的事 —— **面板一旦会撒谎，标定就没有意义了。**

**修法**：在 `updateSlotWithoutHand` 里喂一帧 `slot.flickDetector.update(null, dt)` ——
复用检测器自己的手丢分支（顺带保留冷却，不会因为手抖一下就能连发）。
两条单测钉住：手丢了要清、从"扣住"直接切到"三指张开"也要清。

**教训**：一个"处理缺帧"的分支如果只有单测在调用、生产代码从不触发，
它就不是防线，而是摆设。
