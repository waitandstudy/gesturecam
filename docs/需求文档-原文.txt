GestureCam：手势控制口播素材相机
AI 编程开发提示词 / MVP 产品与技术规划
一、项目目标
我要开发一个手机端视频拍摄工具，主要面向口播、自媒体创作者。
它不是传统的视频剪辑软件，而是一种：
“通过手势，在拍摄过程中直接操控视频中的图片/素材。”
用户打开手机摄像头进行口播，在拍摄过程中通过手势控制预先选择好的图片素材。
例如：
- 手掌出现 → 图片出现
- 手移动 → 图片跟随移动
- 双指张开 → 图片放大
- 双指收拢 → 图片缩小
- 后续可以加入甩出、惯性、碰撞、弹跳等效果
最终用户直接得到已经合成好的视频，不需要再进入剪映/PR设置关键帧。
二、非常重要：不要把程序写死
这是本项目最重要的开发要求之一。
不要为了完成 MVP 而把所有逻辑写死在页面代码里。
当前只开发第一版，但是从架构上必须考虑未来扩展。
未来可能加入：
1. 更多手势
2. 更多图片
3. 视频素材
4. GIF / 动态素材
5. 文字素材
6. 贴纸
7. 3D物体
8. 图片物理碰撞
9. 重力
10. 摩擦
11. 弹性
12. 惯性
13. 图片之间的碰撞
14. 图片与屏幕边界碰撞
15. 图片挂在屏幕顶部
16. 图片通过“绳子”/连接线悬挂
17. 图片跟随手掌
18. 图片跟随手指
19. 图片固定在空间中的某个位置
20. 图片吸附到指定位置
21. 多张图片同时存在
22. 多个图片分别绑定不同的控制方式
23. 自定义手势
24. 用户自定义快捷动作
25. 图片出现/消失动画
26. 图片旋转
27. 图片透明度
28. 图片层级
29. 图片被“扔出去”
30. 图片被“抓住”
31. 图片被“推走”
32. 图片被“弹飞”
33. 图片超出画面
34. 图片从画面外进入
35. 未来可能加入 AR/3D 空间效果
不要把“图片 = 当前手掌位置”这种逻辑直接写死。
应该建立可扩展的“素材对象”和“控制器/行为系统”。
三、第一版 MVP 只做这些功能
1. 摄像头预览
打开 App 后进入摄像头，用户看到实时画面。
2. 添加图片
从手机相册选择图片。
第一版支持 PNG、JPG、WEBP。
每张图片作为独立的素材对象。
3. 手部识别
使用手机端实时手部追踪能力。
优先考虑 MediaPipe Hands 或其他稳定的端侧手部追踪方案。
第一版重点识别：
- 手掌位置
- 手指关键点
- 手掌是否出现
- 两指距离
不要依赖云端 AI。拍摄时必须实时、低延迟、尽量离线。
四、第一版手势
A. 出现/激活
例如 ✋。
检测到指定手势时激活当前图片。
图片从预设状态进入画面。
B. 跟随
图片处于“跟随模式”时：
手掌向左 → 图片向左
手掌向右 → 图片向右
手掌向上 → 图片向上
手掌向下 → 图片向下
必须加入平滑处理，避免手部关键点抖动导致图片疯狂抖动。
C. 双指缩放
检测食指 + 拇指两点距离变化。
距离增加 → 图片放大。
距离减少 → 图片缩小。
缩放应该以两指中心点作为主要参考点，而不是简单以图片左上角缩放。
五、素材对象必须独立设计
每一张图片都应该是一个独立 Material/Object。
建议至少包含：
id
source
position
scale
rotation
opacity
visible
zIndex
anchor
mode
gestureBinding
physicsEnabled
boundaryMode
其中 mode 第一版至少预留：
FOLLOW_HAND
FIXED
TOP_HANGING
虽然第一版可能只真正实现 FOLLOW_HAND 和 FIXED，但架构不要限制以后增加更多模式。
六、图片不一定跟手
未来重要玩法之一是：
让多个图片同时存在，但每个图片有不同的行为。
例如：
- 图片1：固定在顶部
- 图片2：固定在画面某个位置
- 图片3：跟随我的手
不要设计成“一次只能控制一张图片”。
从架构上必须允许：
Scene
 ├── Object 1
 ├── Object 2
 ├── Object 3
 └── ...
每个 Object 都有自己的：
- 位置
- 缩放
- 旋转
- 显示状态
- 控制方式
- 行为
七、顶部悬挂图片
未来非常重要的功能。
例如我想让三张图片同时出现在画面中：
顶部左侧、顶部中间、顶部右侧。
它们可以像挂在屏幕顶部的展示卡片。
未来可以表现成：
顶部
───────────────
 │      │      │
 │      │      │
🖼️     🖼️     🖼️
甚至以后加入：
- 绳子
- 链条
- 摆动
- 弹性
- 重力
- 摇晃
因此请把“悬挂”设计成独立的 Object Behavior，而不是写死在 UI 中。
例如：
HangingBehavior
未来可扩展：
PhysicsHangingBehavior
RopeBehavior
SpringBehavior
八、关于图片能不能超出拍摄框
不要简单写死成“图片永远不能超出摄像框”，也不要写成“图片永远允许无限超出摄像框”。
应该设计成可配置的 Boundary Mode：
CLAMP
图片不能完全离开画面。
ALLOW_OVERFLOW
允许图片超出摄像框。
CENTER_CLAMP
至少保证图片中心点在画面内。
FULL_VISIBLE
尽量保证整个图片都在画面内。
未来还可以加入：
NO_BOUNDARY
第一版默认建议：
CENTER_CLAMP
也就是说：
图片可以有一部分超出画面边缘，但是图片中心点不能完全跑出去。
这样既不会限制用户的操作，又可以避免图片完全消失导致用户找不到。
九、预览区域和交互区域要分离
摄像头画面是 Render Area。
手势识别区域是 Interaction Area。
不要假设图片只能存在于摄像头画面内部。
未来可能出现：
摄像头画面
+
画面外缓冲区域
+
素材进入/离开动画
因此底层 Scene 不应该直接绑定 Camera View 的边界。
应该有：
Scene Coordinate System
以及：
Camera Viewport
二者之间进行坐标转换。
十、图片应该是真正的“对象”
不要把图片当作简单 UI Image。
应该建立 Scene/Object 系统：
Scene
│
├── Camera
├── HandTracker
├── ObjectManager
│    ├── ImageObject
│    ├── ImageObject
│    └── ImageObject
└── Recorder
每个 ImageObject：
Transform
 ├── position
 ├── scale
 └── rotation
Appearance
 ├── texture
 ├── opacity
 └── zIndex
Behavior
 ├── follow
 ├── fixed
 ├── hanging
 └── ...
Interaction
 ├── gesture binding
 └── interaction state
Physics
 ├── velocity
 ├── acceleration
 ├── gravity
 └── collision
Physics 第一版可以关闭，但数据结构应该预留。
十一、第二版本：物理系统
第二版再加入物理。
惯性：
快速移动手，松开后图片继续运动。
重力：
图片自然掉落。
碰撞：
两个图片碰撞后产生反弹。
屏幕边界：
图片可以与边界发生碰撞或反弹。
摩擦：
图片移动一段距离以后逐渐停止。
十二、第三阶段：更丰富的互动
抓取：
手接近图片并抓住它。
扔出：
快速移动手，根据手部速度赋予图片初速度。
推动：
手碰到图片时把图片推走。
多手控制：
左手控制图片1，右手控制图片2。
双手缩放：
两只手拉开 → 图片放大；
两只手靠近 → 图片缩小。
十三、录制系统
最终必须能够把：
Camera Preview
+
Virtual Objects
+
Hand Interaction
+
Effects
直接录制成最终视频。
最终视频应该是合成后的结果。
用户不需要再去剪映里面重新设置图片关键帧。
录制和预览架构不要写死。
需要考虑：
- 录制原始视频
- 录制合成视频
- 导出不同分辨率
- 选择是否显示某个素材
- 录制前预览
- 拍摄后重新编辑对象
- 保存场景
- 重复使用场景
十四、未来可能增加“拍摄前编排”
例如用户拍摄前设置：
图片1
位置：顶部左侧
行为：悬挂
图片2
位置：顶部右侧
行为：悬挂
图片3
行为：跟随手
图片4
行为：固定
然后开始拍摄。
未来可以有：
Scene Template
例如：
财经口播模板
科技口播模板
知识口播模板
第一版不要做复杂 UI，只需要保证架构可以支持。
十五、第一版 UI 要极简
不要做成剪辑软件。
核心界面：
- Camera Preview
- 添加图片
- 开始拍摄
- 必要的素材管理
第一版重点：
1. 添加图片
2. 摄像头
3. 手势识别
4. 图片跟随
5. 图片缩放
6. 图片固定
7. 录制
不要加入：
- 社交

十六、开发原则
原则1：先把核心 Demo 跑起来。
不要一开始做大量 UI。
原则2：核心逻辑模块化。
至少拆分：
CameraManager
HandTrackingManager
GestureManager
SceneManager
ObjectManager
BehaviorManager
PhysicsManager
RecorderManager
AssetManager
原则3：未来可以替换手部识别方案。
不要让 MediaPipe 直接渗透到整个项目。
应该通过：
HandTrackingInterface
提供统一的数据，例如：
Hand
 ├── wrist
 ├── thumb
 ├── indexFinger
 ├── middleFinger
 └── ...
以后更换识别方案时，不需要重写整个程序。
原则4：Behavior 必须可扩展。
禁止大量针对具体图片写死的 if/else。
不要：
if object == image1:
    follow hand
if object == image2:
    stay top
应该是：
Object
 ↓
Behavior
 ↓
BehaviorManager
例如：
FollowHandBehavior
FixedBehavior
HangingBehavior
PhysicsBehavior
ThrowBehavior
未来增加行为时，只需要新增 Behavior。
十七、第一阶段开发任务
Phase 1
建立项目基础架构：
- 摄像头
- 页面
- Scene
- Object
- 基础坐标系统
Phase 2
加入手部追踪：
- 手掌位置
- 食指
- 拇指
- 双指距离
并在屏幕上显示调试点。
Phase 3
实现 ImageObject：
- position
- scale
- rotation
- visible
- zIndex
Phase 4
实现 FollowHandBehavior：
手移动 → 图片平滑跟随。
Phase 5
实现 PinchScaleBehavior：
双指距离 → 图片缩放。
Phase 6
实现多个 Object：
至少支持 Image 1、Image 2、Image 3 同时存在。
并确保每个对象可以拥有不同 Behavior。
Phase 7
实现 FixedBehavior / TopHangingBehavior：
让图片可以固定在左上、顶部、右上、任意位置。
Phase 8
实现 BoundaryMode：
- FULL_VISIBLE
- CENTER_CLAMP
- ALLOW_OVERFLOW
Phase 9
加入录制：
最终能够录制 Camera + Virtual Objects 得到最终视频。
十八、开发过程中非常重要
每完成一个阶段，都先运行测试。
不要：
一次写几千行代码 → 最后再测试。
应该：
实现
 ↓
运行
 ↓
测试
 ↓
修复
 ↓
再实现下一模块
如果发现技术方案存在问题：
先停下来告诉我问题在哪里，以及有哪些方案。
不要为了“完成代码”而自行改变产品设计。
十九、最终产品愿景
这个项目最终不是：
“一个给视频加图片的软件。”
而是：
“一个可以让创作者在拍摄时直接操控虚拟素材的互动口播相机。”
用户面对摄像头：
说话
+
手势
+
虚拟物体
+
物理效果
最终让视频素材像现实世界里的物体一样：
- 可以拿
- 可以拖
- 可以放
- 可以扔
- 可以推
- 可以缩放
- 可以碰撞
- 可以悬挂
- 可以排列
- 可以从画面外进入
- 可以从画面内飞出去
第一版只实现最基础的：
“我用手控制图片。”
但底层架构必须为后续的：
“我在镜头前操控一个虚拟世界。”
留下空间。
二十、当前开发要求
现在请先完成 Phase 1：
项目基础架构 + 摄像头预览 + Scene/Object 基础系统。
完成后再进入下一阶段。
不要一次性把所有未来功能实现。
