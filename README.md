# GestureCam

手势控制的口播素材相机。拍摄过程中直接用手操控画面里的图片素材，最后直接得到合成好的视频，
不用再去剪映/PR 里给图片设关键帧。

**当前进度：Phase 9 收尾 + 手势文法落地**（Phase 1 基础架构 + 坐标系统 + 手机端适配；
Phase 2 手部追踪 + 手型判定；Phase 4 跟随手感；Phase 5 双手缩放；Phase 8 边界约束；
手势文法与指弹删除见 `docs/手势文法.md`）。

已能跑通的完整闭环：**摄像头 → MediaPipe 手部关键点（双手）→ 手型判定 → 捏合选中素材 →
抓取偏移跟随 → 双手开合缩放 → 指弹删除 → 握拳急停 / 松手释放 → 录制成片**。

| 已完成 | 说明 |
| --- | --- |
| Phase 1 | 摄像头预览、Scene/Object、坐标系统、行为管线、时间轴数据模型 |
| Phase 1.5 | 手机端：9:16 成片画幅、letterbox、安全区、后台恢复 |
| Phase 2 | MediaPipe Tasks HandLandmarker（GPU/CPU，**支持两只手**）、480p 降采样、One-Euro 平滑 + 重新捕获重置、**手型判定（捏合/握拳/张开）+ 指弹检测**、手丢失宽限、骨架调试点 |
| Phase 4（核心） | `FollowHandBehavior`：死区 + 增益 + 帧率无关平滑。**没有它，捏合能抓住素材但素材不会动**（见 `docs/DECISIONS.md` 第 12 节） |
| Phase 5 | `TwoHandScaleBehavior`：一只手拿住素材，**两只手一起开合**改大小，带死区与上下限（第 18 节说明了为什么从单手改成双手） |
| Phase 8 | `BoundaryBehavior`：五种 `BoundaryMode` 在 `constrain` 阶段真正生效 —— 素材拖不出画幅，永远抓得回来 |
| 手势文法 | **捏合＝鼠标左键、握拳＝Esc、指弹＝删除**：双维度手型判定、握拳按手取消、取消后重新武装（`docs/手势文法.md`） |
| Phase 9（核心） | 录制：离屏导出画布（固定 720×1280 成片分辨率、无黑边无调试叠层）+ MediaRecorder + 麦克风音轨 + 每帧写 timeline；录完弹结果面板可直接预览与保存（见第 13 节） |
| 录制护栏 | 时长 5 分钟 / 体积 400MB 上限，80% 起预警，到点**自动停止并保存**；**切到后台也自动停录保存**（不是"录到一半崩掉"） |

**现在可以完整跑通产品闭环**：打开摄像头 → 添加图片 → 捏合选中 → 单手拖动 →
另一只手捏上、两手开合缩放 → 指弹删掉不要的图 → 握拳急停（或松手）→ 点拍摄 → 拿到一个 mp4。

**操作方式**（核心是"捏合＝鼠标左键"；准星旁会写出系统认定的手型）：

| 动作 | 鼠标类比 | 效果 |
| --- | --- | --- |
| 拇指与食指捏合（准星压在素材上） | 左键按下 | 选中素材（素材边框变绿） |
| 捏着移动 | 按住拖动 | 拖动素材（**只改位置，绝不动大小**；拖到边上会被画幅挡住，不会丢） |
| 另一只手也捏合 | 按住 Shift | 进入双手缩放：出现青色虚线**缩放宽轴** |
| 两只手一起张开 / 收拢 | — | 放大 / 缩小（宽轴上标出实时倍率） |
| 第二只手松开 | 松开 Shift | 大小**停在原地**（不回弹），退回单手拖动 |
| **食指勾住再快速弹出（指弹）** | **拖进废纸篓** | **删掉指尖下的那张图**；它会先半透明淡出 2 秒，**期间再捏住就撤销** |
| **握拳（抓着素材的那只手）** | **Esc** | **立即停止这只手的操作**：取消会话，素材停在原地（另一只手不受影响） |
| 松开捏合 / 抓着素材的那只手张开手掌 | 左键抬起 | 释放 |

**握拳急停之后必须先张开手掌才能重新抓取**（否则取消动作本身会立刻抓回一张图，
急停等于没用）。屏幕上会写明「已取消 · 张开手掌后可以重新抓取」。

为什么缩放要两只手：单只手的捏合**同时**表达了位置（两指中点）和大小（两指距离），
两个自由度在运动学上无法分开，手一抖两个一起变 —— 真机反馈就是"缩放一直颤、不好把控"。
双手把它彻底解耦，而且两手间距的基准大一个数量级，相对噪声小十倍。

为什么握拳要用"食→中夹角"当第二判据：握拳时拇指压在食指上、两指尖距离同样很小，
只看这**一个**维度必然把急停读成"想抓取"。夹角是相对量，握拳时食、中两指一起蜷曲、
共同项抵消，所以它仍然很小 —— 于是"捏"和"拳"变成两个可分的手型。
完整推导见 `docs/DECISIONS.md` 第 18 节，文法规格见 `docs/手势文法.md`。

**录制后的保存**：按钮会按设备能力自动选择 ——
手机上走**系统分享面板**（选「存储到照片」才会进相册），
桌面走**另存为对话框**，都不支持时才退化成普通下载；
面板上会明确写出文件会去哪（"下载不会进相册"是最容易被误解的一点）。
另有一个「下载」按钮作为永远可用的备选。

新加入的素材默认 `FOLLOW_HAND` —— 添加图片、捏合抓住、拖到想要的位置，这是这个产品的核心承诺。

## 快速开始

```bash
pnpm install
pnpm dev          # http://localhost:5173
```

打开页面会请求摄像头权限，随后加载手部识别模型（本地 7.8MB，首次稍慢）。
把拇指和食指捏合即可抓取素材。底部「9:16」按钮可切换成片画幅。

| 命令 | 说明 |
| --- | --- |
| `pnpm dev` | 开发服务器（`host: true`，同一局域网可访问） |
| `pnpm typecheck` | TypeScript 严格模式检查 |
| `pnpm test` | 单元测试（348 个） |
| `pnpm build` | 类型检查 + 生产构建（会把 wasm 拷进 `dist/wasm`） |
| `node tools/verify-browser.mjs` | **浏览器端验收**：无头 Edge + 虚拟摄像头 + CDP，76 项含像素级断言、真实录制、准星/准入窗口/双手缩放/手型判定/急停/边界/指弹删除与装填门槛/录制上限与切后台，外加六张人工过目截图 |

### 真机测试（手机）

手机浏览器（**不要用微信内置浏览器**）打开页面时，摄像头权限只在 **https** 下可用。
局域网地址 `http://192.168.x.x` 拿不到 `getUserMedia`，所以开发阶段用 https 隧道：

```powershell
# cloudflared 放在仓库外（放仓库里会让 vite 监听它并因文件占用而崩）
$a = "$env:LOCALAPPDATA\GestureCam\tools"
& "$a\cloudflared.exe" tunnel --url http://localhost:5173 --no-autoupdate
```

命令会打印一个 `https://xxx.trycloudflare.com` 地址（**每次重启都会变**），手机直接打开即可。
微信内置浏览器、部分国产浏览器对 WebAssembly + getUserMedia 的组合支持不全，请用系统浏览器。

> 真机测试注意：iOS Safari 和 Android Chrome 的 `getUserMedia` 都要求安全上下文，
> `http://192.168.x.x` 局域网地址拿不到摄像头。需要用 https 隧道，详见 `docs/DECISIONS.md` 第 8 节。

> 开发环境注意（踩过一次的坑）：这台机器上的 `pwsh` 实际是 **Windows PowerShell 5.1**，
> `Get-Content`/`Set-Content` 默认按 GBK 处理，**不要用它读写源码文件**，
> 否则中文会被写坏且不可逆。改文件一律用编辑工具，或显式用
> `[System.IO.File]::ReadAllText($p, [System.Text.Encoding]::UTF8)`。

## 架构要点

**管线**（每帧严格按此顺序，顺序本身就是架构）：

```
CameraManager → HandTrackingInterface → GestureManager
    → InteractionManager（手势落到具体素材）→ Scene/ObjectManager
    → BehaviorManager（input → simulate → constrain → present）
    → Renderer → Recorder
```

**不写死**是两条硬规则：

1. **素材的行为通过挂载 Behavior 表达**，禁止 `if (object.id === 'image1')`。
   加"惯性/重力/碰撞/甩出/悬挂"只需注册一个新 Behavior 类型。
2. **素材的交互能力是数据**（`state.interaction = { grabbable, scalable, rotatable }`），
   InteractionManager 里没有任何"这张图特殊"的分支。

**行为看不到原始手部关键点**，只能看到手势层的输出和本帧交互状态 ——
由类型系统强制，避免"每个 Behavior 里都长出一套自己的手势逻辑"。

**素材状态是可序列化的纯数据**，所以"保存场景 / 场景模板 / 拍后重编辑 / 离线重合成"
都不需要改数据结构。

详细决策与理由（含坐标语义、手机端适配、与需求文档的偏离、外部项目许可证核实）见
[`docs/DECISIONS.md`](docs/DECISIONS.md)；
手势的含义与阈值见 [`docs/手势文法.md`](docs/手势文法.md)；
参考 handy 源码的具体结论见 [`docs/handy-借鉴笔记.md`](docs/handy-借鉴笔记.md)。

## 手部识别（Phase 2）要点

**参数全部标定过，不是拍脑袋定的**（依据 handy 的实测经验，见 `docs/handy-借鉴笔记.md` §2）：

| 项目 | 取值 | 理由 |
| --- | --- | --- |
| 手数 | 追踪 2 只、手势层 2 个槽位 | 双手缩放要求两只手都在捏合；任何一层只留 1 手，双手就永远不成立 |
| 平滑 | One-Euro `minCutoff 1.2 / beta 0.03 / dCutoff 1.0` | 静止时消抖、快速移动时低延迟，固定系数滤波做不到两者兼顾 |
| 重新捕获 | 手腕一帧内位移 > 整帧的 **25%** → 整组滤波器重置 | 手不可能这么快，这一定是 MediaPipe 认错手/重新捕获；不重置就会"滑"过去 0.4 秒，而双手缩放基准正好在这段时间被采样 |
| 捏合判定 | `gap = 拇食指距离 ÷ 掌心长度 < 0.50` **且**（食指伸展 **或** 食→中夹角 > 25°） | **尺度无关**：手离摄像头远近读数一致。第二个维度用来把"捏"和"拳"分开（握拳的 gap 同样很小） |
| 捏合退出 | `gap > 0.60`（迟滞） | 曾经是 1.00，那是为"单手张开手指放大"留的余量；缩放交给双手后收紧到 0.60，误判明显变少 |
| 手型判定 | `FIST`（**食指+中指**深蜷）优先于 `PINCH`；`FIST`/`OPEN` 需连续 2 帧 | 急停优先于选中。握拳只认食指+中指：**中指不参与捏合**，捏得紧时无名指小指本来就会蜷进掌心，要求四指会把握拳和"深层捏合"混起来（真机踩过） |
| 检测输入 | 等比降到 **480p** 以内 | 模型内部本来就缩到 ~200px，喂全帧只是白烧算力 |
| 运行模式 | `VIDEO` + 严格递增时间戳 | 模型要求；同一毫秒重复调用会自增兜底 |
| 手丢失 | 0.25s 宽限期内仍算按住，但**不给位置** | 追踪偶发丢帧不能打断拖动；交互层据此冻结素材 |
| 抓取准入 | 起手须压在素材上，或起手后 **0.7s** 内移进素材 | 照顾"先捏上、再把手移到图片上"的自然动作顺序 |
| 抓取宽容边距 | 输出画幅短边的 **8%** | 手指中点精确压在小素材上很别扭，差一点点就不该白费一次捏合 |
| 槽位认领 | 先按**左右手标签**，再按上一帧位置就近 | 只按就近匹配会因平局把两只手对调槽位 → 抓着手的那只手会多发一次 `gesture-start`，把抓取断掉（第 18.3 节） |
| 手指蜷曲判据 | 平面 `≤1.10` **且** 含深度 `≤1.20` | 真拳头 ≈0.95–1.05，放松手 ≥1.2。两把尺子同时成立才算蜷曲（握拳会锁住操作，最不该误判） |
| 双手缩放基准 | 取**未平滑**的两手间距（原始关键点） | "张开→捏合"时捏合中点会移动 3–4% 掌长，平滑值要 0.26s 才追上；用平滑值当基准素材会自己变大 6% |
| 指弹装填 | **拇指扣住食指尖** `gap ≤0.65` + 其余三指蜷着 `middleReach ≤1.10`，连续 2 帧（**不看食指**） | 第五轮真机标定推翻了旧模型：弹脑瓜蓄力时食指是伸着的（实测 1.52），而拇指就压在食指尖上（gap 0.45）。旧门槛要求"拇指躲开"，方向是反的。详见 `docs/手势文法.md` §9.1 |
| 指弹释放 | 3 帧内 `gap` 相对装填时张开 `≥0.25`、其余三指仍蜷着、指尖速度 `≥0.8` | 真机 20fps 下一次指弹只跨 1–2 帧。速度门槛从 1.5 调低是因为旧值按"指尖走画幅宽 10–20%"估，实际只走 3–7% |
| 边界约束 | `constrain` 阶段统一钳制，按 `boundaryMode` 五种策略 | 跟手/缩放/物理都跑在它前面，只有最后一步收口才不会漏；外加"完全跑出画幅就拉回中心"的兜底 |
| 录制上限 | 时长 5 分钟 / 体积 400MB，80% 起预警；切后台自动停录 | MediaRecorder 把整段视频攒在内存里，没上限就是"录到一半崩掉、前面全丢"；后台时画布不再更新，继续录只会得到冻结画面 |

**屏幕上有常驻的手部准星叠层**（`render/handOverlay.ts`）：准星画在素材**之上**，
并高亮"现在捏下去会抓到的那个素材"；每只手的捏合连线都会画出来（这样用户能确认
"第二只手被认到了"），双手成立时再画一条虚线**缩放宽轴**并标出实时倍率；
准星旁还会写出**系统当前认定的手型**（捏合/握拳/张开），
握拳或"已取消待重新武装"时给一条横幅。
这不是装饰 —— 素材盖住手之后，用户看不见自己的手指，准星是他唯一的瞄准依据；
"要张开另一只手"这个动作没有宽轴提示绝大多数人第一次根本想不到；
"系统认为我的手是什么"是用户判断"是自己动作不到位还是程序认错了"的唯一依据。
该叠层**永不进成片**（导出画布是另一个渲染器）。

几个刻意的设计选择：

- **检测节奏与渲染解耦**：渲染跑满 rAF，检测按约 30fps 自己的节奏跑，两次检测之间沿用连续量。
  一次性事件（`gesture-start` / `gesture-end`）只投递一帧，避免 60fps 渲染重复触发抓取。
- **判定用原始关键点，位置用平滑关键点**：判定要低延迟（捏下去就要抓），位置要稳。
  试过给判定单独配一条快滤波，但它会把"张开→捏合"拖上 2 帧，破坏单帧响应的性质。
- **行为看不到原始关键点**：`BehaviorContext` 里只有手势层的输出和交互状态，由类型系统强制。
- **急停是状态不是事件**：`controls.fistHands` 每帧都在，取消动作天然幂等 ——
  做成事件的话，一旦被合并/丢失，急停就失效了。
- **两条降级路径**：GPU delegate 失败自动退 CPU（打一行提示）；单帧检测失败只记数不中断渲染循环。

**已知的性能事实**：无头 Edge 里 `detect()` 约 21–33ms/帧（输入 853×480，**两只手**）。
但无头环境用的是软件光栅（SwiftShader），这个数字是**上界**，真机 GPU 上应显著更快 ——
真机数字需要手机实测（见 `docs/DECISIONS.md` 第 11 节）。
**追踪两只手的推理开销还没在真机上量过**，这是下一次真机验证要看的第一项。

**开发用后门**（仅 `import.meta.env.DEV`）：`window.gesturecam` 暴露了
`handTracker` / `gestures` / `injectRawHands()` / `setGestureOverride()`，
用于没有真手时（例如无头浏览器、或调跟随手感时）驱动整条链路。
验收脚本正是靠它跑通了"手势 → 交互 → 行为 → 对象"这一整条链。
